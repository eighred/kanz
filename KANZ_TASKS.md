### Sovereign control plane — the committed product direction (2026-07-13)

_**Supersedes PS-01…PS-07 (cancelled 2026-07-13).** The end-user marketplace direction — consumer portal, fund discovery catalog, retail onboarding/funding, SaaS billing tiers — is off the roadmap. kanz is a B2B institutional execution platform: a tenant runs its own funds on its own exchange accounts, and what it needs is a control plane over them, not a storefront. `services/web-bff` stays built and parked._

_Each line below is committed DIRECTION, not decomposed work: it promotes to a 1–3 day TODO task only after a ground-truth verification when its turn comes. The caveats are what the code actually says today — the design brief describes several things that do not exist, and they are named here so nobody plans against them._

- **SOV-01 · Identity hierarchy + capability ACL** (`root@universe` → tenant master → sub-user RW/RO). **Ground truth: none of this hierarchy exists.** Identity today is a FLAT `roles` claim with one `API_GATEWAY_REQUIRED_ROLE` at the gateway (OIDC/JWT), SPIFFE mTLS between services, and `app.tenant_id` at the database. There is no sub-user provisioning, no RW/RO split, and **no SSH-public-key-fingerprint identity anywhere** — the brief's handshake model is not what the platform does. The work is a CAPABILITY model at the gateway (the sole identity authority), not role strings; an RO principal must be unable to reach a write route BY CONSTRUCTION, with the arch tests failing the build if one is reachable without a write capability. Decide first whether identity stays OIDC-at-the-edge (delivered, and what Eighred SSO issues) or moves to SSH keys — do not build both.
- **SOV-02 · Fund-basket collateral segregation — DELIVERED (EXEC-M16).** An exchange liquidates per ACCOUNT, so a basket is segregated by its exchange account or not at all. `venue_account_id` is now a FACT on every order, fill and ledger entry; `OMS_VENUE_ACCOUNTS` binds each portfolio to its account exclusively; the OMS refuses to start on an account shared by two portfolios; the router cannot reach another portfolio's credential; and the engine refuses a ledger write that will not declare which account it moves. **And the adapter no longer takes its own word for it (SOV-02a, DONE):** `venue.v1.Describe` reports the account, the adapter proves it against the exchange at boot (Binance/OKX `uid`) and refuses to serve orders if the key belongs elsewhere, and the OMS refuses to start on an adapter that names a different account than it was declared as. This line is closed.
- **SOV-03 · Sovereign telemetry** — cross-tenant NAV / growth / fee / slippage view for the operator of the whole estate. Ground truth: the ledger IS bitemporal (`effective_time` + `knowledge_time` on `ledger_entries`, with a replay-as-of fold), so the curves are computable; what does not exist is a cross-tenant read path, and RLS makes that deliberately hard. Building it means an explicit, audited privileged surface — NOT a bypass of `app_current_tenant()`, which is the one guarantee the whole multi-tenancy story rests on.
- **SOV-04 · License revocation / node wipe (the kill-switch).** Ground truth: **does not exist.** No license, no `WipeNodeConfiguration` RPC. The primitive to build it on is `kanz-halt` — a control signal every pod learns, including one booting tomorrow. **Design constraint, learned the hard way:** it must be a BROADCAST on a compacted stream with no max-age, never a consumer group (a group delivers to one pod, and a restarted pod resumes past the only message that mattered — that is how the halt gate once turned every rolling restart into a trading outage).
- **SOV-05 · Operator TUI + remote node deployment.** Ground truth: **no TUI exists**, and nothing pushes binaries over SSH. The images ARE already distroless, static, `-trimpath -ldflags="-s -w"`, cosign-signed and digest-pinned; the deploy path is Kubernetes + GitOps. Decide whether the estate is k8s-managed (delivered) or SSH-pushed hosts (new) before building an operator surface for either — two deployment models is the parallel system this repository does not build.
- **SOV-06 · Push telemetry back to TradingView.** Ground truth: the chart surface is PULL — authorized clients poll `/v1/broker/accounts/{id}/…` through the gateway (EXEC-M15), which is why it can be authenticated at all. tv-sync's SSE `/stream` is deliberately not proxied: the gateway buffers with `io.ReadAll`. An outbound push channel is a NEW egress path (new NetworkPolicy egress rule, new place proprietary execution logic could leak) and must carry the minimum — instrument, side, size, entry — and nothing about how the decision was made.

## DONE

_Historical record — one line per completed epic. Full implementation detail is in git history; durable decisions are in `KANZ_BRAIN.md`._

### Phase 11 — Automated fund-management & multi-exchange execution system (opened 2026-07)

- **SEC-M2** — **any principal who could READ could TRADE.** The gateway is the platform's sole identity authority, and it wrapped ALL of `/v1` in one chain with one check (`middleware.Auth(authn, cfg.RequiredRole)`, a single `HasRole`): `GET /v1/portfolios/{id}/exposure` and `POST /v1/orders` were guarded IDENTICALLY. **The token handed to an analyst to look at the fund's exposure would submit an order to a live exchange.** SEC-M1 closed the door to strangers; this is what the people INSIDE may do. Capabilities are now declared AT REGISTRATION and enforced by the router: `authz.Mux.Handle` takes the capability as a REQUIRED PARAMETER, so a route cannot be added without deciding who may call it — not because a reviewer would catch it, but because **the code would not compile**. Enforcement wraps the handler at registration rather than sitting in a chain a future composition root could forget. Two capabilities, deliberately (`Read`, `Trade`): a capability system nobody can hold in their head gets bypassed by the first engineer in a hurry. The HTTP verb is NOT the authority on effect — `POST /v1/portfolios/{id}/scenario` computes a what-if and moves no capital, so it is a Read; the capital path is exactly `POST /v1/orders` and `POST /v1/orders/{id}/cancel`. **The arch test is the deliverable, not the routes**: it asserts `Trade` over WHATEVER `internal/orders` registers (so a route added there tomorrow is covered the moment it exists), and a golden table over the whole gateway that FAILS THE BUILD on any undeclared route — the decision "who may call this?" is made deliberately, once, in the open, instead of being inherited by accident from whichever mux the handler landed on. Both mutations were verified to bite: declaring `POST /v1/orders` as `Read` fails the build, and so does adding an undeclared `POST /v1/orders/{id}/amend`. Grants are deny-by-default with no fallback — an unmapped role decays to nothing, not to "well, it authenticated, so let it read" — and the gateway REFUSES TO START if `API_GATEWAY_TRADE_ROLE` is unset (a trading outage dressed as a control is discovered by an order that quietly did not go out; a crash is discovered by whoever deployed it) or if it EQUALS the baseline role (every authenticated caller carries that one, so SEC-M2 would be undone by a config edit that looks harmless in a diff).

- **EXEC-M21** — **tv-sync's book was LOST on every restart, and a trader would have been the one to find out.** tv-sync folds the fund's orders, executions, positions and P&L into memory and serves them to TradingView over the Broker API. There was NO DATABASE anywhere in the service, and its bus consumer is a DURABLE GROUP: a restarted pod resumes at its last ack and never re-reads what it already folded. **A pod roll left the trader looking at an EMPTY ACCOUNT** — no positions, no orders, zero P&L — while the fund's real positions sat open at the exchanges. The board assumed EXEC-M20's compacted position FACTs would rebuild it; ground truth disproved that (tv-sync consumes ORDER LIFECYCLE events, not position FACTs). Worse, and new: **nothing on this platform durably retained those FACTs either.** The EXECUTION stream that carries `order.>` has a 24h max-age, no archiver exists, and no table anywhere persists a fill (`position_fills` holds only fill_ids, for the exactly-once claim) — so replaying the stream from its start would rebuild AT MOST YESTERDAY, and realized P&L since inception was simply gone. tv-sync now durably records **the FACTs it folds** (`tv_facts`, one migration, tenant-scoped under FORCE RLS) and replays them through the SAME fold at boot, BEFORE the HTTP server binds and before the consumers start. **The store holds FACTs, never a book** — persisting orders and positions would have made tv-sync a SECOND BOOK that could disagree with the OMS's, with nobody able to say which was right; a log of its own input cannot drift from the truth because it holds no opinion about it, and `KANZ_BRAIN.md`'s zero-truth decision survives intact. Replay follows `seq`, the order the facts were *folded*: the fold is order-dependent (an average-cost basis depends on which fill came first), so a rebuild that reordered them would produce a DIFFERENT book — a subtler failure than losing it. The FACT is recorded BEFORE it is folded, and `ON CONFLICT (tenant_id, event_id) DO NOTHING` makes the fold exactly-once across a redelivery — which also fixed a live bug: a redelivered `accepted` used to append a duplicate order revision. A FACT that cannot be recorded is NACKed, never folded (folding it would put it in RAM and nowhere else, while the durable group acked it and never sent it again). tv-sync now REFUSES TO START without a fact log: an ephemeral book is not a degraded mode, it is a lie with a delay on it. Proven against a real Postgres under a non-superuser role: a pod folds two fills and dies, a fresh pod rebuilds the identical positions, executions, orders and realized P&L — and with the rebuild neutered, the test reproduces the production failure verbatim ("the trader sees an empty TradingView account while the fund holds 1 BTC"). Consequence, deliberate: tv-sync joins the platform's per-tenant deployment convention (`TV_SYNC_TENANT`, a tenant-scoped pool), as every other durable service already does.

- **EXEC-M19b** — **the trading loop could OPEN a position and could not CLOSE one.** `cmd/webhook-ingest/main.go` wired `Positions: ingest.StaticPositions{}` — an EMPTY MAP — under the comment *"M1 sim: flat by default; M3+ binds the OMS projection"*. M3+ never bound it. So `translate.legSizeAndSide` sized every flatten leg from a position of ZERO, the fan-out skipped every leg, and a `close` alert produced **no orders at all while the webhook answered 202 Accepted**: a strategy that opened a position and later told Kanz to close it was silently ignored, and the position stayed open. Every guard against that had been built and none of them fired, because the code path was never reached. The stub is retired: webhook-ingest now folds the OMS's per-venue position FACTs (EXEC-M19a) off the compacted POSITION stream into a `PositionCache`, armed at boot by `bus.SubscribeBroadcastReady` — new to `pkg/bus`, and the piece that was missing: `SubscribeBroadcast` could replay the book but could not say WHEN it had, and a pod that answers a CLOSE mid-replay sizes it against a book it has only half-learned. **An unarmed cache REFUSES rather than reporting flat** (`ErrPositionsNotArmed` → 503, nonce RELEASED so the alert is redelivered rather than burned): "I have not learned the book" and "the fund holds nothing" are different facts, and rendering the first as the second is exactly how a CLOSE gets swallowed — the original bug, one layer down. Readiness gates on the same signal, so a pod that does not know what the fund holds stays out of its Service and is never handed a signal that closes it. Proven against a live NATS: a COLD-BOOTING pod learns 0.6 BTC at BINANCE and 0.4 at OKX from the replay alone — the current state, not the superseded 9 BTC the compacted subject overwrote — and a `close` over the real source emits two SELLs sized 3/5 and 2/5, each venue flattening what IT holds. Sizing both legs from the fund's total would over-sell at each exchange and flip a flat position into a naked short.

- **EXEC-M19a** — the platform could not say how much BTC it held AT OKX. A fund holding 1 BTC at Binance and 2 at OKX holds TWO DIFFERENT THINGS: you cannot sell the OKX BTC on Binance. But the position book keyed on `(portfolio, instrument)` alone, so the second venue's fill OVERWROTE the first — the book said 2 and the fund had 3, and nothing anywhere could say where they were. **`order.v1.Fill` has carried `venue` all along; the projector threw it away.** What it cost: `translate.legSizeAndSide` sizes a CLOSE leg from the position AT THAT VENUE, and there was no such number to give it — which is why webhook-ingest's CLOSE path is wired to an EMPTY map and a `close` alert produces ZERO orders. The book is now keyed `(tenant, portfolio, venue, instrument)` — the finest true grain, and the same axis EXEC-M16 established for collateral (an exchange margins and LIQUIDATES per account, and an account belongs to a venue). **The fund-level view is not lost, it is DERIVED**: one book, projected twice in the same transaction — the aggregate on `risk.position.changed` (its consumers, the risk engine and the compliance monitor, UNTOUCHED and unable to lose a venue) and the per-venue holding on the new `risk.position.venue.changed`, which the execution plane binds. Two tables would have been two truths, and the day they disagreed nobody could say which one the fund held. The aggregate's average price is COST-WEIGHTED across venues — a fund's basis in BTC is what it paid for all of it, not what it paid at whichever exchange filled last. `PositionState.venue` is additive (field 9, empty on the aggregate: it belongs to no single exchange), and both FACTs ride the existing compacted POSITION stream (`risk.position.>` already carries them), so there is no topology change — and the two subjects diverge at the third token, so the aggregate's wildcard cannot swallow the per-venue FACTs and make a monitor fold one venue as though it were the fund. A fill with no venue is REFUSED (`ErrFillHasNoVenue`): a holding that belongs to no exchange is one no CLOSE could ever reach, and every venue adapter stamps it. Proven against a real Postgres under a non-superuser role; red-green: drop the venue from the key and **OKX reports holding 3 BTC when it holds 2** — a CLOSE there would over-sell by one and flip a flat position into a naked short.

- **EXEC-M20** — a position is STATE, and its subject did not say which position it was. Every position FACT rode the flat `risk.position.changed` on the 24h `RISK` stream, and that is wrong twice over: **JetStream compacts PER SUBJECT**, so a flat subject retains ONE message for the entire platform — `DeliverLastPerSubject`, the mechanism a booting consumer uses to learn current state in a single read, returned one instrument's position and silence about every other — and a **24h max-age** meant a holding that had not traded today simply AGED OFF THE STREAM. What it cost: the post-trade compliance monitor's book is in-memory, filled by a durable consumer group that resumes at its last ack, so a RESTARTED monitor came back with a PARTIAL book and evaluated every mandate against it. **A fund holding an instrument its mandate FORBIDS looked compliant, because the holding was not there to see.** The control did not fail; it went blind. This is the mandate defect (EXEC-M13) on a different stream, and it gets the same fix: one subject per (tenant, portfolio, instrument), a dedicated **POSITION** stream (`--max-msgs-per-subject=1`, **no max-age** — a position must not age out, for the same reason a mandate must not), and consumers that ARM at boot by `SubscribeBroadcast`. `RISK` is narrowed from the `risk.>` wildcard so the two streams do not overlap (JetStream forbids a subject belonging to two streams) — guarded, not gambled: `test/arch`'s `TestEverySubjectIsCarriedByAStream` walks the AST for every subject the code names and fails the build if one goes unbound, and it caught the load-seeder still publishing the flat subject. The subject builder lives in `internal/platform/subject` beside the token sanitizer — **not** in `internal/risk/ingest`, because the OMS publishes it and compliance consumes it, and the RISK-02 boundary forbids outsiders importing risk internals (the arch test caught that too, exactly as designed). **Scope, honestly:** this fixes the monitor's RESTART hole; it does not lift its `replicas: 1` pin, because broadcast means every pod folds every position and would emit its own duplicate breach FACT. **And the board was wrong about tv-sync** — it consumes ORDER LIFECYCLE events, not position FACTs, and folds executions into its Broker-API book, so compacted positions would not rebuild its execution history. It needs its own task; see below. Proven against a REAL broker: a monitor consumes the fund's holdings, is RESTARTED, and still raises the breach on the forbidden instrument — red-green, a durable group instead of broadcast and the restarted monitor raises nothing. The production bootstrap script applies cleanly on a real broker (`RISK` and `POSITION` coexist, no overlap), and the POSITION stream comes up with `max_msgs_per_subject=1` and `max_age=0`.

- **EXEC-M18** — the OMS published ABSOLUTE positions computed from HALF the fills. `position.Book` was `map[key]*lot` behind a mutex — in memory, per pod — and the projector consumed fill FACTs through a durable consumer **GROUP**, which LOAD-BALANCES. `oms-deploy.yaml` ships **`replicas: 2`**. So each pod folded only the fills it happened to receive, held a PARTIAL book, and published `domain.v1.PositionState` on `risk.position.changed` as an **ABSOLUTE** quantity. **This is worse than a control that fails, because a projection does not merely fail to act — it SPEAKS**, and the risk engine, the compliance monitor and tv-sync all believed it. So did the OMS's OWN PRE-TRADE GATE: `main.go` handed the same in-memory book to `compliance.NewBookSource`, so every order was projected onto a book missing whatever the other pod had folded — and a concentration limit evaluated against half a fund's positions does not refuse loudly, it quietly says yes. On restart the map came back EMPTY, so the next 0.1 BTC fill published `position = 0.1` while the fund held 5.1. EXEC-M7c made the ORDER store durable and declared `replicas: 2` safe; it made the admission gate safe and left the book exactly where it was. The book is now a `position.Store` — `Book` (in-process, one replica, and it says so) or `Postgres` — the same shape `order.Store` took, not a second pattern. Each fill folds in ONE transaction: claim the `fill_id` (`INSERT … ON CONFLICT DO NOTHING`; RowsAffected 0 ⇒ a redelivery or the other pod already folded it ⇒ **skip**, never count a trade twice), lock the lot `FOR UPDATE` so two pods serialize at the engine instead of racing in two address spaces, apply the SAME weighted-average-cost fold (one implementation — two would be two chances to disagree about a fund's basis), upsert. Decimals are exact `RatString` TEXT, the stance the accounting ledger already takes; the WAC arithmetic stays in Go. A fill with no `fill_id` is REFUSED (`ErrFillNotIdentified`) rather than folded un-dedupable — every venue stamps one, so an empty id is a producer defect, and silently double-counting a fill is how a fund's position drifts from the exchange's. Both stores now come from ONE pool and one DSN and degrade together: no `OMS_DATABASE_URL` ⇒ both in-process ⇒ one replica, WARNed at boot. Proven against a real Postgres under a NON-SUPERUSER role (so RLS is enforced, not bypassed), red-green: revert the durable load and pod B publishes **2** when the fund holds **3**, and the restarted pod publishes **1/10** when it holds **5.1** — the exact numbers this task was written from.

- **EXEC-M17** — the replay defence was one pod's memory, and it ate the signal it failed to send. The nonce cache — the thing standing between a re-delivered TradingView alert and a SECOND set of live orders — was a `map` in one process. Two pods are two maps: the re-delivery lands on the other replica, is admitted, and fans out again. The OMS's admission gate cannot close it, because a fresh nonce mints a fresh `signal_id` and therefore fresh `order_id`s — the duplicate is invisible as a duplicate. That is what pinned `webhook-ingest`, **the one service the internet talks to**, to a single replica: a single point of failure on the loop's front door. It now claims against a shared store (`NonceStore`), so a re-delivered alert is a replay wherever it lands. **The bug nobody had named is the second one.** `Authenticate` CONSUMED the nonce — and everything after it could still fail: the halt gate, the size resolution, and `Emit`, which is what actually publishes the FACT and the orders. There was no release path. **So a transient broker error burned the nonce permanently**: the alert had traded nothing, and any redelivery of it was refused as a replay. A live trading signal, lost, silently, because NATS blinked — the exact loss EXEC-M7b's three-phase lease was built to prevent ("claim-and-never-release turns a failed handler into a lost event"), on the one path where the event is a trade. The nonce is now a LEASE: **committed when the platform reached a VERDICT** on the alert (emitted it, or deliberately refused it) and **released when it FAILED TO DECIDE** (broker down, size unpriceable) — and the retry is safe by construction, since `signal_id = DeterministicID(strategy, nonce)` re-derives the same idempotency keys and the broker collapses whatever did land. A halt still BURNS the nonce, deliberately and unchanged: an alert that fired during a halt is stale by the time the halt clears, and re-firing it into a moved market is worse than dropping it — a previous engineer decided that on purpose and pinned it in a test, and it was not silently reversed. **The store is `NonceStore`, not `bus.Deduper`, for exactly one reason: `bus.RedisDedup` FAILS OPEN.** That is right for bus dedup — it suppresses duplicate WORK, and an outage should degrade to doing the work twice rather than halting consumption — and it is catastrophic here, where the store IS the replay defence on the path that submits orders to a live exchange. A Redis outage would admit every replayed alert. So this one FAILS CLOSED, on the halt gate's own logic (EXEC-M6): *"I cannot tell whether this alert already traded"* must never resolve to *"trade it"*. A bool cannot carry "I don't know", so its claim returns an error, and the server answers **503, never the 200 "duplicate ignored"** — telling TradingView we handled an alert we refused would drop a live signal on the floor over a Redis blink. The in-process store is still there for one replica, but it is now an **EXPLICIT admission** (`WEBHOOK_INGEST_ALLOW_INPROCESS_NONCE`): the process REFUSES TO START without it, because a per-pod replay defence reachable by FORGETTING to configure Redis is indistinguishable from a correct one — and the deployment that forgot is the one an autoscaler quietly takes to N pods. Proven against the real binary: no Redis and no admission ⇒ **exit 2**, naming the double-trade; admitted ⇒ boots, WARNing that it must run exactly one replica; `-tags redis` with a bad URL ⇒ **exit 2**, never a silent fallback to the per-pod map. - **SOV-02a** — the adapter's account was a claim, and everyone believed it. - **EXEC-M16** — the ledger segregated collateral the exchange does not. Basket Alpha and Basket Beta had separate books and ONE collateral pool. An exchange margins, nets and **LIQUIDATES per ACCOUNT** — the OKX sub-account, the Binance account behind one API credential; the ledger has always kept cash per **PORTFOLIO**. Not imprecise: **WRONG, in the direction that loses money.** The platform can now answer two questions it could not ask — *which account did this order execute against* (a FACT: `venue_account_id`, on the OrderState, every Fill, every LedgerEntry) and *which accounts may this portfolio spend from* (a CONTROL: `OMS_VENUE_ACCOUNTS` binds (tenant, portfolio, venue) → account). Proven end to end in-cluster, alert to FACT: fund-chart (bound) FILLED carrying `venueAccountId: sim:XNAS` on the fill AND the order state; fund-other — mandated, but bound to no account — REJECTED with `VENUE_ACCOUNT_UNBOUND` and no book at all. **Not closed**: the adapter's declared account is TAKEN ON TRUST — it holds the credential but does not report which account the key belongs to, so a mis-declared endpoint posts fills to the wrong account's ledger rows while the exchange debits the right one (SOV-02).

- **EXEC-M14** — an ungoverned portfolio is no longer silent. - **EXEC-M12** — every restart silently halted the platform. A test now reads the path each venue manifest tells the kubelet to poll and drives the REAL probe handler with THAT path while publishing is broken, requiring a 503 — so `/healthz` fails (it stays 200 when the bus is gone, which is what liveness is *for*) and so does the gRPC port. **(3) CI had never run a single real-bus test**: it provisioned Postgres but no broker, so `TEST_NATS_URL` was unset and every NATS integration test silently skipped — including the EXEC-M7a guard written precisely because a fake publisher cannot fail like a broker. CI now starts JetStream and sets it. **(4) Two things blocked that, both fixed:** `webhook-ingest`'s loop test needed a live NATS *and* a running OMS but gated only on the first, so it did not skip when CI had NATS without an OMS — it FAILED, waiting 15s for fills from a service nobody started (a test must gate on ALL its preconditions); and the `translate` real-bus test was FLAKY — `defer setupConn.Close()` ran BEFORE the registered cleanups, so its `DeleteStream` fired on a torn-down connection, the stream survived with its messages, and the next run failed. It passed on a fresh broker and failed on every repeat, which is exactly how a flaky CI is born.

- **DATA-M8c** — the vendor feed; the master fills. `feed.RefSource` had no implementation: survivorship, crosswalk, conflict detection, projection, the durable oversight queue and exact-decimal pricing were all delivered and tested, and the projector had nothing to project. The transport is a **mounted vendor file drop** — which is how institutional reference data is actually delivered (Bloomberg Data License, Refinitiv DataScope publish scheduled flat-file extracts to SFTP; the fund mounts the drop). For a security master that is not a fallback for a "real" API, it IS the real integration, and it is the one an ops team can operate: the file that produced today's master is still on disk tomorrow, which is what an auditor asks for. It is also **the only transport verifiable end to end without a commercial account** — and an adapter nobody can execute is an adapter nobody should trust, which is the lesson of every defect on this branch. A vendor with a REST reference API implements the same seams beside it; nothing downstream changes. Also landed the **price half of the seam** (`PriceSource`/`PriceAdapter`/`FilePriceSource`), which `reference.go` always asserted existed ("price arbitration is fed by the market-data price adapters, not the reference feed") and which had no implementation either — a separate source, not extra columns on `RefRow`, because reference and price are different files with different cadences and folding them together would force a full reference re-delivery to update a price. Both adapters share ONE `IDResolver`, which is what makes a price land on the instrument the reference feed mastered. **`DATAMASTER_VENDOR_PRIORITY` has no default** and a reference vendor without one is a startup error: whose ISIN wins when two vendors disagree is a decision about who the fund believes, and this service will not quietly make it for them. **Nothing is silently dropped** — an unkeyable row, an unparseable or non-positive price, a price with no `as_of` (it could never be aged for staleness), a missing file: each fails the delivery naming vendor/file/line, and the all-or-nothing rule leaves the last good projection standing. A missing file is NOT an empty extract ("the vendor sent nothing" and "we could not read what the vendor sent" are different facts). Verified end to end against live Postgres with three vendor drops: the master fills, survivorship pulls AAPL's description from ICE because Bloomberg left it blank (with per-field provenance), the consensus is the exact median `"480.2"` of three quotes, ICE's fat-fingered 600 is flagged at 24.95%, and a deliberate ISIN disagreement is filed as IDENTIFIER_CONFLICT.

- **DATA-M8b** — a price is money, and datamaster's were doubles. `pricing` held every price on the path as `float64` — the vendor candidate, the arbitrated consensus, and the price a human chose when overriding a break — defending it as "a comparison over candidate values, a derived oversight statistic". Both halves were false: `feed.NormalizePrice` **publishes the consensus to the market plane as the instrument's Quote** (it is the mark, not a statistic), and DATA-M8a had just made the override **durable**, so a named human's decision was being written to an append-only compliance record as a rounded binary double. Every value here is a sum, a quotient, a median or a comparison of exact decimals — all four keep a rational exact, and there is no sqrt anywhere to earn the honest float exception the FRTB capital path takes. Now `*big.Rat` end to end via `internal/dec`, with rounding introduced in exactly one place (`dec.ToProto`, at the wire). **The median of 0.10 and 0.20 is now exactly 0.15; as float64 it was 0.15000000000000002** — a mark no vendor quoted. The tolerance test became a multiplication (`|price − consensus| > tolerance · |consensus|`), so a candidate exactly ON the 5% line decides deterministically instead of on whichever way the last binary rounding fell. `exception_overrides.chosen_price` went from `DOUBLE PRECISION` to `TEXT` holding the exact RatString — the house stance for money (accounting's `ledger.quantity/price`, alternatives' `commitment.amount`) — in a **new** migration, because 0001 is checksummed and may be applied somewhere; verified against live Postgres, where `123456789.123456789` round-trips exactly and the double column returned `123456789.12345679`. The API refuses a JSON number for `chosen_price` (an IEEE-754 double by definition) and emits every price as a decimal string. It also refuses a price carrying MORE precision than `common.v1.Decimal`'s scale — found by driving the running binary, where a 15dp override was stored exactly and then displayed as `130.12345679` by every surface: an audit record whose value nobody can ever see is the same bug in a new costume. And a candidate with no price no longer votes a zero into the median (a silent vendor has not quoted zero) — it raises MISSING_PRICE against its source.

- **DATA-M8a** — the golden store had no writer. `store.PostgresGolden`, `store.PostgresExceptions`, `master.Resolve` and `pricing.Arbitrate` all shipped with MASTER-01, all tested, and **nothing ever constructed or drove them**: `golden_records` had no writer, the read API called `master.Resolve` over the live vendor feeds *inside every request*, and the pricing-oversight exception queue — the surface a human works — was a `map` behind a mutex. New `internal/projector` is the consumer: it pulls every vendor on a cycle, resolves one golden record per instrument, persists it, and files every break into the durable exception store; the read path now serves what was mastered rather than mastering as a side effect of being read. **Three defects were real regardless of feeds.** (1) **Operator overrides did not survive a restart** — an override is a named human accepting a price the system flagged, and it lived in that map; the append-only `exception_overrides` table (actor, reason, identity `seq`) existed and was wired to nothing, so a rolling update silently deleted a compliance record. Proven fixed by `kill -9` against a live non-superuser Postgres: the override survives, and a re-detected break does **not** re-open behind it (the deterministic exception id + `ON CONFLICT DO NOTHING` preserve the review state a human already gave it). (2) **A price was arbitrated against the whole book** — `pricing.Candidate` carried no instrument id, so a feed's entire price list went to `Arbitrate` for whichever instrument was asked for; with the test fixture the consensus for INST1 came back as **115**, the median of INST1's quotes *and another instrument's 999*. Candidates now carry what they are a price of. (3) **A vendor outage would have quietly rewritten the master** — survivorship resolves each field from the highest-priority vendor that *has* it, so projecting over a subset does not yield a partial record, it yields a **different** one, sourced from a fallback and stamped with provenance as though intended; a refresh is now all-or-nothing and the store keeps the last good projection. **The fabrication guard (4th instance)**: canned `SimFeed` records, once resolved into `golden_records`, are indistinguishable from mastered vendor data and are trusted as an instrument's identity by everything downstream — the service now refuses to start with a sim feed unless `DATAMASTER_ALLOW_SIM` is set (the market-ingest shape: a simulator reachable by forgetting a flag). `app.tenant_id` is set at the composition root (the accounting bug class), verified against FORCE RLS: the projected row is invisible both to a session with no tenant and to a different one. _Carried forward: `feed.RefSource` still has no implementation, so the pipe is empty — an empty master, not an invented one. The price path stays float64 and therefore has **no** durable price store (DATA-M8b)._

- **EXEC-M7c** — durable order state; the OMS is no longer single-replica-for-correctness. `order.Store`'s only implementation was `MemoryStore`, whose atomicity is a mutex in one process — so `Store.Create`, the atomic admission gate standing between a duplicated `SubmitOrder` and a duplicated venue order, evaporated the moment a second OMS pod existed (two pods, two maps, both `Create` succeed, both route to the venue). `order.Postgres` enforces admission **at the engine** — `INSERT ... ON CONFLICT (tenant_id, order_id) DO NOTHING` with `RowsAffected() == 0 ⇒ ErrExists`, never a `SELECT` followed by an `INSERT` — reusing the risk-engine's `persist` stance (pgxpool, `app.tenant_id` GUC, FORCE RLS under a non-superuser role) rather than inventing a second durable-state pattern. `oms-deploy.yaml` carries `replicas: 2` with the DSN mounted from a CSI/Vault file (SEC-01d), which is the whole point: the guarantee is now cross-pod because it is enforced by a unique index, not by a mutex.

- **EXEC-M7b** — two-tier atomic dedup; the double-trade window is closed. Concurrent redelivery of one event could run its handler twice, and on the order path the handler is *route the order to the venue*. **Tier 1 (`pkg/bus`)**: `Deduper` was `Seen()`+`Record()` — a check-then-act, where two deliveries of one key both passed `Seen` before either `Record`ed. The split existed for a real reason (`Record` ran only after a *successful* dispatch, so a handler failure could not poison the window against retries), and a bare `SETNX` would have destroyed it: claim-and-never-release turns a failed handler into a **lost event**. The contract is now a three-phase lease that keeps both properties — `Claim` (atomic, one `SET NX EX` round-trip, exactly one concurrent winner), `Commit` (success ⇒ hold for the full window), `Release` (failure ⇒ the redelivery really does retry) — with a 5s lease so a worker that dies mid-dispatch has its claim expire rather than swallowing the event forever. Every consumer exit path commits or releases; Redis errors still fail OPEN. **Tier 2 (`services/oms`)**: the bus was never the only hole, and fixing it alone would not have closed this — bus dedup keys on `idempotency_key`, so a re-submit under a *fresh* event id is invisible to it. The OMS's own "idempotent re-submit" guard was `Load()`-then-`Save()`, the same check-then-act, and what runs immediately after it is `s.work()` → `router.Route()` → **the venue**. Two concurrent deliveries both saw `ErrNotFound`, both admitted, and both traded; the state converged (`Save` upserts) so it *looked* idempotent. `Store.Create` is now the atomic admission gate (`ErrExists` ⇒ ack and stop, before the venue). The sharedstate contract test tolerated 25% duplicate leakage on the grounds that idempotent handlers were the real guarantee — **both halves were false**; it now asserts exactly-once and is deterministic (10/10 under `-race`, where it previously leaked 33–60% and flapped). The OMS gained a *concurrent* resubmit test counting real venue executions — the existing idempotency test was sequential, which is why it passed while the bug was live.

- **EXEC-M7a** — the signal→order path could not publish on a real spine. Two independent defects, each of which dropped **every** StrategySignal FACT and SubmitOrder COMMAND on the floor of a live broker. (1) `payload_schema_ref` was never set: `bus.Validate` requires it on every envelope, `Producer.stamp` copied it through verbatim, and no caller on this path supplied one — but this was never `translate`'s bug alone. **Twelve** publish sites across nine files omitted it: the whole signal→order path, every OMS venue connector/recon/userdata emitter, market-ingest's book snapshots, the gateway's order route. Fixed at the **producer**, not at twelve call sites — the ref is not new information (the convention is exactly `{proto full name}:{schema_version}`, and the producer already holds the payload message *and* a `SchemaVersion` that `Validate` independently requires to be ≥1), so it now derives one when the caller omits it, with an explicit ref still winning. A required field the producer can compute itself should never have been the caller's job to remember, and asking twelve callers to remember it is how all twelve forgot. (2) **No JetStream stream was bound to `strategy.>` or `order.>`** — `bus.Publish` is a *JetStream* publish, so an unbound subject is a hard failure, not fire-and-forget. Both now ride the `EXECUTION` stream, added to its subject list rather than renamed under `execution.>` (a rename would break every consumer binding and the replay log's subject history). **Why the suite never caught either:** every unit test on this path injects a fake `capture` Publisher that satisfies the interface and never validates — a fake Publisher cannot fail the way a broker fails. `translate` now carries a real-bus integration test that drives `Emit` through a real Producer over real JetStream and reads both events back; it was verified to fail with the exact production error when the producer fix is reverted.

- **EXEC-M6a/b** — the kill-switch, and the handle to pull it. The `Halted` seam was wired to a **constant `false`** and set by no binary, while `pkg/alpha`'s Runner ticked engines every 100ms with no brake at all — `kill -9` was the risk control. Now one shared **`translate.Gate`**, held by both brains and checked at the webhook perimeter *and* at the top of every alpha tick (engines are not even evaluated while halted — a halted system decides nothing, rather than deciding and discarding). **Deny-by-default**: constructed CLOSED, and only `OPERATING_MODE_NORMAL` trades. **Fail-closed**: a NATS disconnect trips it — `pkg/bus` could not even *observe* a disconnect before (`MaxReconnects: -1` heals silently), so `NATSConfig` gained `OnDisconnect`/`OnReconnect`, with `ClosedHandler` covering the terminal case the disconnect handler misses. **Latching**: reconnection does not clear it and neither can a `system:`-issued ModeChanged; only an operator does — matching `lifecycle.v1`'s own contract that HALTED "requires intervention to leave". The gate is a **required** field in `translate.Options`, because the seam it replaced was optional, defaulted open, and was never wired: an optional brake is an absent brake, and the compiler now refuses to build a translator without one. Keys off the existing **`lifecycle.v1.ModeChanged`** (`component="system"`), NOT a new status enum — a second one would be the parallel system the gate exists to prevent. An undecodable halt FACT trips the gate: "I could not read the brake signal" must never resolve to "keep trading". `cmd/kanz-halt` is the operator's standalone break-glass handle, sharing no code with the trading pipeline (the subject constant lives in a zero-dep `internal/platform/mode` that both ends import) — the one tool that must work while the system is on fire cannot be coupled to the system that is on fire. It rejects `--resume --by system:…` at the flag boundary, since the gate would ignore it and the resume would silently no-op. Verified against a live NATS/JetStream spine, both directions.

All four tag combos green; default binaries still vendor-free.
