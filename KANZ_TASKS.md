Now added as `BlackLitterman(BLInput) → μ` in `internal/optimization` — a **μ-producer, not a new objective**: it starts from the market-equilibrium prior `Π = δΣw_mkt` (the returns that make the market-cap portfolio optimal — reverse optimization) and tilts it by investor **views**, then the result drops into `MarketInputs.ExpectedReturns` and the EXISTING `MaxSharpe`/`MaxReturn` runs unchanged. **The load-bearing numerical choice: the Idzorek/He-Litterman form**, which inverts only the **k×k** view system (k = number of views, usually 1–5) via the existing `solveLinear` and **never inverts Σ** — `μ_BL = Π + τΣPᵀ·(PτΣPᵀ + diag(Ω))⁻¹·(Q − PΠ)`. **Ω is a per-view diagonal** (views assumed independent; a full correlated k×k Ω is a documented non-goal); a 0 entry ⇒ the He-Litterman default `(PτΣPᵀ)_ii`, which scales *with* the prior variance along the view, so a near-zero-variance view degrades gracefully to `μ → Π + Q/2` rather than blowing up (the robustness the whole-branch review specifically verified). Views are general **P-rows** (absolute "A returns 5%" and relative "A beats B by 2%" alike); `k=0` (no views) ⇒ `μ_BL = Π` exactly. Fail-loud throughout: `δ≤0`, `τ≤0`, dimension mismatch, or a singular `M` ⇒ a sentinel error, never a NaN/partial μ. **Wired end-to-end**: an optional `black_litterman` block on the HTTP `/v1/propose` computes `μ_BL` and feeds it into the existing `Optimize`/`Rebalance` path (BL error ⇒ 400); the BL-absent path is byte-for-byte unchanged. No new `ObjectiveType`, **no proto change** (BL is a request shape, like the other propose fields). Proven against exact hand-computed references (no-views ⇒ `δΣw_mkt`; a single absolute view ⇒ 0.125; a relative long-short view widens the spread toward `q`; Ω-confidence monotonicity; a bullish view through the service raises the asset's target above equilibrium). Shipped subagent-driven: 2 TDD tasks, each task-reviewed (the BL algebra independently re-derived) and a whole-branch review returning SHIP; build/vet/gofmt clean, `test/arch` unchanged. **This completes the RISK-M2 optimizer epic** (HRP + BL). Three input-validation follow-ups the reviews surfaced (module-wide Σ-PSD precondition, the `/v1/propose` body limit, the zero-variance IVP guard) are consolidated into OPT-HARDEN.

- **RISK-M2a** — **the optimizer could not diversify without trusting return estimates.** The optimizer shipped a real solver (mean-variance / min-variance / max-Sharpe tangency / risk-parity) but every objective either needs μ (the hardest input to estimate) or, like min-variance, concentrates and inverts an ill-conditioned Σ. Grep-verified absent: **Hierarchical Risk Parity** (López de Prado). Now added as the `HRP` `ObjectiveType`: correlation-distance → single-linkage clustering → quasi-diagonal ordering → recursive bisection by cluster variance (the full sub-covariance quadratic form). **It uses only Σ — no expected returns — and never inverts Σ**, which is the numerical robustness that motivates it. Reachable through the existing HTTP `/v1/propose` with **no service change** (the service decodes the internal `Objective` type from JSON, not the proto enum); `OBJECTIVE_TYPE_HRP=5` was added to `optimization.proto` for mirror-honesty only (nothing consumes it in Go). **The load-bearing decision (approved): pure HRP — box bounds are NOT applied**, unlike its sibling `RiskParity` which projects onto `[lo,hi]`; projecting would distort the risk allocation into something that is no longer HRP, so HRP returns its natural long-only, fully-invested weights and mandate compliance is validated downstream by the existing `CheckMandate` (a book you cannot hold is rejected there, not silently reshaped). Proven against exact hand-computed references (2-asset ⇒ the inverse-variance split `[0.8,0.2]`; a 4-asset two-correlated-pair universe ⇒ `[0.4,0.4,0.1,0.1]`), the long-only + sum-to-1 invariants (proven to hold for any tree shape, not just power-of-two universes), the diversification property vs min-variance, and every numeric edge (n=1, zero-variance, degenerate Σ — no NaN, no inversion). **A flawed test caught during execution:** the diversification test's first covariance was block-diagonal, which makes HRP and global min-variance *provably identical* at the cluster level (equal within-cluster variances force 50/50; between-cluster both allocate ∝ 1/cluster-variance) — the implementer proved the identity via TDD and added a cross-cluster covariance term so the property could actually manifest, rather than weakening the assertion. **Black-Litterman was split out to RISK-M2b** (a μ-producer, a different seam). Shipped subagent-driven: 2 TDD tasks, each task-reviewed (spec + quality, the deviation independently re-derived) and a whole-branch review returning SHIP; build/vet/gofmt clean, `test/arch` unchanged. - **RISK-M1** — **the tail measures a risk desk asks for immediately after VaR did not exist.** The engine shipped calibrated VaR (historical-sim + Monte-Carlo, Kupiec/Christoffersen backtest, liquidity-adjusted, factor models, XVA) and a real optimizer — but grep-verified absent across the whole Go tree were **CVaR/Expected Shortfall, drawdown, and concentration (HHI)**: the first questions asked after "what is my VaR?". Shipped subagent-driven: 5 TDD tasks + a fix wave, each task-reviewed (spec + quality) and a whole-branch review returning SHIP; build/vet/gofmt clean, `test/arch` unchanged, the deferred perf note (each returns-backed measure re-reads the provider; a request-scoped memo is the future optimization) documented and left as a follow-up.

- **DATA-M2** — **the log of record was landed, but nowhere permanent: `lake-sink` was fully written and had never been deployed.** DATA-M1 gave Kafka a producer; the log it fills is still bounded — `order.order` et al. age out at 30 days and the compacted STATE topics (`compliance.mandate`, `risk.position`) keep only the latest value per key. Its unit tests (decode round-trip, CDC land/ack/NAK, Hive partition layout) need no broker and were already covered by `go test -race ./...`; no new integration stanza. **This closes the data-durability foundation: the log of record now holds the log, and the lakehouse now keeps it.**

- **DATA-M1** — **the durable log of record had no producer: nothing had ever written an event to Kafka.** `bus.DialKafka` had exactly ONE non-test caller in the whole repository — `lake-sink`, and it SUBSCRIBES. Every service dialed NATS and only NATS. So the broker, the provisioned topics, the per-tenant ACLs, the MirrorMaker2 DR replication and the whole of `lake-sink` were built and waiting on a producer that was never written — and `EXECUTION` (which carries `order.>`) has a 24h max-age, so realized P&L since inception, the audit trail and every fill older than yesterday were retained NOWHERE. The archiver is that producer: one durable consumer per in-scope stream (money, mandates, positions, inference, platform, data — NOT market ticks, which are re-fetchable and highest-volume, nor 1h-ephemeral observability), mapping each envelope to its Kafka topic off the envelope's `event_type` (NOT the subject) and producing it VERBATIM keyed on `partition_key`. **It acks NATS only after Kafka acknowledges** — a failed produce NACKs and redelivers (at-least-once; `event_id` is the dedup header), because acking an event you failed to archive is the silent permanent loss the service exists to end. **The topic topology was almost entirely fiction** and was rebuilt from ground truth: only 4 of the 16 `{domain}.{entity}` names the code actually publishes on had a topic, and 9 provisioned topics had no publisher at all — now guarded by `TestEverySubjectHasAKafkaTopic`, which is CROSS-LANGUAGE (the Go AST walker cannot see the two subjects `kanz-py` publishes, so a Go-only guard would be blind to them — the identical drift AI-M1 found on `tenant_id`) and fails the build if a published subject has no topic. **`replicas:1` + `Recreate` on purpose**, the OPPOSITE call from webhook-ingest's EXEC-M22: single writer keeps per-key order correct by construction, and a gap here is deferred catch-up work (NATS retains the events), not signal loss. **Fail-closed has a terminal state now (Task 5b):** a transient produce failure retries forever (Kafka down ⇒ never drop), but a structurally-unmappable event (bad `event_type`, cross-tenant, reserved prefix) is dead-lettered to `dlq.archiver` and acked — otherwise it NAK-loops forever with no `MaxDeliver`. **The loop surfaced a fleet-wide bus bug:** `bus.NATSClient.Subscribe` ended with `cc.Stop()`, which DISCARDS buffered messages, so on every restart in-flight messages were stranded server-side for a full 30s `AckWait` while their NACKed siblings redelivered first — reordering the log on an ordinary deploy; fixed to `Drain()` (regression test 14/20 fail against `Stop()`, 40/40 pass against `Drain()`), and the archiver's `Run` was found to subscribe only its FIRST subject (a blocking per-subject call in a sequential loop) — one stream archived out of fifteen, a healthy-looking pod retaining almost nothing. **The ordering contract, decided under fire:** the archiver guarantees DURABILITY (nothing lost) and LOCALITY (same key ⇒ same partition), but NOT Kafka-partition-position order across a sustained outage (repeated NAKs are re-scheduled by JetStream out of order, server-side, unfixable from the client) — the authoritative per-key order is the envelope's own ordering fields, which an order-dependent consumer sorts by. Lag is a first-class metric (`kanz_archiver_pending_messages`), because an archiver silently falling behind its max-age is loss with a delay on it. Proven against a REAL NATS and a REAL Kafka: events land in the right topic in per-key order, a Kafka outage loses nothing and catches up clean, and the ack-before-produce red twin genuinely loses every event. NetworkPolicy denies the archiver any path to the OMS, the venues or webhook-ingest — it reads the spine and writes the log, nothing near the capital path.

- **SEC-M2** — **any principal who could READ could TRADE.** The gateway is the platform's sole identity authority, and it wrapped ALL of `/v1` in one chain with one check (`middleware.Auth(authn, cfg.RequiredRole)`, a single `HasRole`): `GET /v1/portfolios/{id}/exposure` and `POST /v1/orders` were guarded IDENTICALLY. **The token handed to an analyst to look at the fund's exposure would submit an order to a live exchange.** SEC-M1 closed the door to strangers; this is what the people INSIDE may do. Capabilities are now declared AT REGISTRATION and enforced by the router: `authz.Mux.Handle` takes the capability as a REQUIRED PARAMETER, so a route cannot be added without deciding who may call it — not because a reviewer would catch it, but because **the code would not compile**. Enforcement wraps the handler at registration rather than sitting in a chain a future composition root could forget. Two capabilities, deliberately (`Read`, `Trade`): a capability system nobody can hold in their head gets bypassed by the first engineer in a hurry. The HTTP verb is NOT the authority on effect — `POST /v1/portfolios/{id}/scenario` computes a what-if and moves no capital, so it is a Read; the capital path is exactly `POST /v1/orders` and `POST /v1/orders/{id}/cancel`. **The arch test is the deliverable, not the routes**: it asserts `Trade` over WHATEVER `internal/orders` registers (so a route added there tomorrow is covered the moment it exists), and a golden table over the whole gateway that FAILS THE BUILD on any undeclared route — the decision "who may call this?" is made deliberately, once, in the open, instead of being inherited by accident from whichever mux the handler landed on. Grants are deny-by-default with no fallback — an unmapped role decays to nothing, not to "well, it authenticated, so let it read" — and the gateway REFUSES TO START if `API_GATEWAY_TRADE_ROLE` is unset (a trading outage dressed as a control is discovered by an order that quietly did not go out; a crash is discovered by whoever deployed it) or if it EQUALS the baseline role (every authenticated caller carries that one, so SEC-M2 would be undone by a config edit that looks harmless in a diff).

- **AI-M1** — **the platform's entire AI capability was a contract with nothing behind it, and the 15-layer AI brief was to be built on top of that.** `kanz_inference` shipped a gRPC servicer with admission control, a bus streaming worker, a point-in-time feature store (which correctly refuses future leakage), a permutation-Shapley explainer, a model registry with an MLOPS-01a promotion gate, shadow execution, validation and governance. The tenant now propagates like lineage and BOTH validators require it. Proven live: the engine publishes a feature vector and a real prediction comes back on the bus in 0.51s carrying value, confidence, NORMAL mode and a genuine Shapley attribution. **A prediction is an OBSERVATION, never an order** — it sits downstream of the risk emit, its failures are its own, and NetworkPolicy denies it any path to the OMS or webhook-ingest. Wiring a model to capital is a separate decision, and it has not been taken.

- **EXEC-M22** — **the entrance to the trading loop was ONE POD on `Recreate`: every deploy was a signal-loss window.** `webhook-ingest` receives every TradingView alert, and it was pinned to `replicas: 1` with `strategy: Recreate` — so every rolling update, node drain and pod eviction took the platform's entrance **fully offline**, and an alert arriving in that window hit nothing and was never retried. Mutation-verified: drop the `NX` from the claim and the suite reports the double trade. **And a fail-open was caught by running the manifest rather than reading it:** `--requirepass "$(cat …)"` with a missing secret expands to `--requirepass ""` and Redis comes up **with no password at all** — it now refuses to start instead. Residual, stated on the board: one Redis instance, failing closed.

- **EXEC-M21** — **tv-sync's book was LOST on every restart, and a trader would have been the one to find out.** tv-sync folds the fund's orders, executions, positions and P&L into memory and serves them to TradingView over the Broker API. There was NO DATABASE anywhere in the service, and its bus consumer is a DURABLE GROUP: a restarted pod resumes at its last ack and never re-reads what it already folded. **A pod roll left the trader looking at an EMPTY ACCOUNT** — no positions, no orders, zero P&L — while the fund's real positions sat open at the exchanges. The FACT is recorded BEFORE it is folded, and `ON CONFLICT (tenant_id, event_id) DO NOTHING` makes the fold exactly-once across a redelivery — which also fixed a live bug: a redelivered `accepted` used to append a duplicate order revision. A FACT that cannot be recorded is NACKed, never folded (folding it would put it in RAM and nowhere else, while the durable group acked it and never sent it again). tv-sync now REFUSES TO START without a fact log: an ephemeral book is not a degraded mode, it is a lie with a delay on it. Proven against a real Postgres under a non-superuser role: a pod folds two fills and dies, a fresh pod rebuilds the identical positions, executions, orders and realized P&L — and with the rebuild neutered, the test reproduces the production failure verbatim ("the trader sees an empty TradingView account while the fund holds 1 BTC"). Consequence, deliberate: tv-sync joins the platform's per-tenant deployment convention (`TV_SYNC_TENANT`, a tenant-scoped pool), as every other durable service already does.

- **EXEC-M19a** — the platform could not say how much BTC it held AT OKX. A fund holding 1 BTC at Binance and 2 at OKX holds TWO DIFFERENT THINGS: you cannot sell the OKX BTC on Binance. - **EXEC-M20** — a position is STATE, and its subject did not say which position it was. Every position FACT rode the flat `risk.position.changed` on the 24h `RISK` stream, and that is wrong twice over: **JetStream compacts PER SUBJECT**, so a flat subject retains ONE message for the entire platform — `DeliverLastPerSubject`, the mechanism a booting consumer uses to learn current state in a single read, returned one instrument's position and silence about every other — and a **24h max-age** meant a holding that had not traded today simply AGED OFF THE STREAM. This is the mandate defect (EXEC-M13) on a different stream, and it gets the same fix: one subject per (tenant, portfolio, instrument), a dedicated **POSITION** stream (`--max-msgs-per-subject=1`, **no max-age** — a position must not age out, for the same reason a mandate must not), and consumers that ARM at boot by `SubscribeBroadcast`. `RISK` is narrowed from the `risk.>` wildcard so the two streams do not overlap (JetStream forbids a subject belonging to two streams) — guarded, not gambled: `test/arch`'s `TestEverySubjectIsCarriedByAStream` walks the AST for every subject the code names and fails the build if one goes unbound, and it caught the load-seeder still publishing the flat subject. The subject builder lives in `internal/platform/subject` beside the token sanitizer — **not** in `internal/risk/ingest`, because the OMS publishes it and compliance consumes it, and the RISK-02 boundary forbids outsiders importing risk internals (the arch test caught that too, exactly as designed). **Scope, honestly:** this fixes the monitor's RESTART hole; it does not lift its `replicas: 1` pin, because broadcast means every pod folds every position and would emit its own duplicate breach FACT. **And the board was wrong about tv-sync** — it consumes ORDER LIFECYCLE events, not position FACTs, and folds executions into its Broker-API book, so compacted positions would not rebuild its execution history. It needs its own task; see below. Proven against a REAL broker: a monitor consumes the fund's holdings, is RESTARTED, and still raises the breach on the forbidden instrument — red-green, a durable group instead of broadcast and the restarted monitor raises nothing. The production bootstrap script applies cleanly on a real broker (`RISK` and `POSITION` coexist, no overlap), and the POSITION stream comes up with `max_msgs_per_subject=1` and `max_age=0`.

- **EXEC-M18** — the OMS published ABSOLUTE positions computed from HALF the fills. `position.Book` was `map[key]*lot` behind a mutex — in memory, per pod — and the projector consumed fill FACTs through a durable consumer **GROUP**, which LOAD-BALANCES. `oms-deploy.yaml` ships **`replicas: 2`**. So each pod folded only the fills it happened to receive, held a PARTIAL book, and published `domain.v1.PositionState` on `risk.position.changed` as an **ABSOLUTE** quantity. **This is worse than a control that fails, because a projection does not merely fail to act — it SPEAKS**, and the risk engine, the compliance monitor and tv-sync all believed it. So did the OMS's OWN PRE-TRADE GATE: `main.go` handed the same in-memory book to `compliance.NewBookSource`, so every order was projected onto a book missing whatever the other pod had folded — and a concentration limit evaluated against half a fund's positions does not refuse loudly, it quietly says yes. On restart the map came back EMPTY, so the next 0.1 BTC fill published `position = 0.1` while the fund held 5.1. EXEC-M7c made the ORDER store durable and declared `replicas: 2` safe; it made the admission gate safe and left the book exactly where it was. The book is now a `position.Store` — `Book` (in-process, one replica, and it says so) or `Postgres` — the same shape `order.Store` took, not a second pattern. Each fill folds in ONE transaction: claim the `fill_id` (`INSERT … ON CONFLICT DO NOTHING`; RowsAffected 0 ⇒ a redelivery or the other pod already folded it ⇒ **skip**, never count a trade twice), lock the lot `FOR UPDATE` so two pods serialize at the engine instead of racing in two address spaces, apply the SAME weighted-average-cost fold (one implementation — two would be two chances to disagree about a fund's basis), upsert. Decimals are exact `RatString` TEXT, the stance the accounting ledger already takes; the WAC arithmetic stays in Go. A fill with no `fill_id` is REFUSED (`ErrFillNotIdentified`) rather than folded un-dedupable — every venue stamps one, so an empty id is a producer defect, and silently double-counting a fill is how a fund's position drifts from the exchange's. Both stores now come from ONE pool and one DSN and degrade together: no `OMS_DATABASE_URL` ⇒ both in-process ⇒ one replica, WARNed at boot. Proven against a real Postgres under a NON-SUPERUSER role (so RLS is enforced, not bypassed), red-green: revert the durable load and pod B publishes **2** when the fund holds **3**, and the restarted pod publishes **1/10** when it holds **5.1** — the exact numbers this task was written from.

- **EXEC-M17** — the replay defence was one pod's memory, and it ate the signal it failed to send. The nonce cache — the thing standing between a re-delivered TradingView alert and a SECOND set of live orders — was a `map` in one process. Two pods are two maps: the re-delivery lands on the other replica, is admitted, and fans out again. The OMS's admission gate cannot close it, because a fresh nonce mints a fresh `signal_id` and therefore fresh `order_id`s — the duplicate is invisible as a duplicate. That is what pinned `webhook-ingest`, **the one service the internet talks to**, to a single replica: a single point of failure on the loop's front door. It now claims against a shared store (`NonceStore`), so a re-delivered alert is a replay wherever it lands. **The bug nobody had named is the second one.** `Authenticate` CONSUMED the nonce — and everything after it could still fail: the halt gate, the size resolution, and `Emit`, which is what actually publishes the FACT and the orders. There was no release path. **So a transient broker error burned the nonce permanently**: the alert had traded nothing, and any redelivery of it was refused as a replay. A live trading signal, lost, silently, because NATS blinked — the exact loss EXEC-M7b's three-phase lease was built to prevent ("claim-and-never-release turns a failed handler into a lost event"), on the one path where the event is a trade. The nonce is now a LEASE: **committed when the platform reached a VERDICT** on the alert (emitted it, or deliberately refused it) and **released when it FAILED TO DECIDE** (broker down, size unpriceable) — and the retry is safe by construction, since `signal_id = DeterministicID(strategy, nonce)` re-derives the same idempotency keys and the broker collapses whatever did land. A halt still BURNS the nonce, deliberately and unchanged: an alert that fired during a halt is stale by the time the halt clears, and re-firing it into a moved market is worse than dropping it — a previous engineer decided that on purpose and pinned it in a test, and it was not silently reversed. **The store is `NonceStore`, not `bus.Deduper`, for exactly one reason: `bus.RedisDedup` FAILS OPEN.** That is right for bus dedup — it suppresses duplicate WORK, and an outage should degrade to doing the work twice rather than halting consumption — and it is catastrophic here, where the store IS the replay defence on the path that submits orders to a live exchange. A Redis outage would admit every replayed alert. So this one FAILS CLOSED, on the halt gate's own logic (EXEC-M6): *"I cannot tell whether this alert already traded"* must never resolve to *"trade it"*. A bool cannot carry "I don't know", so its claim returns an error, and the server answers **503, never the 200 "duplicate ignored"** — telling TradingView we handled an alert we refused would drop a live signal on the floor over a Redis blink. The in-process store is still there for one replica, but it is now an **EXPLICIT admission** (`WEBHOOK_INGEST_ALLOW_INPROCESS_NONCE`): the process REFUSES TO START without it, because a per-pod replay defence reachable by FORGETTING to configure Redis is indistinguishable from a correct one — and the deployment that forgot is the one an autoscaler quietly takes to N pods. Proven against the real binary: no Redis and no admission ⇒ **exit 2**, naming the double-trade; admitted ⇒ boots, WARNing that it must run exactly one replica; `-tags redis` with a bad URL ⇒ **exit 2**, never a silent fallback to the per-pod map. Cross-pod claiming, the atomic single-round-trip claim (32 pods racing one alert, exactly one wins), and the fail-closed refusal are driven against a fake `bus.RedisClient`; a live Redis is infra-gated, and the manifest's `replicas: 1` stays until one exists — but it is now a stated admission that moves in one change with the flag, not a property of the code.

- **SOV-02a** — the adapter's account was a claim, and everyone believed it. - **EXEC-M16** — the ledger segregated collateral the exchange does not. Basket Alpha and Basket Beta had separate books and ONE collateral pool. - **EXEC-M7b** — two-tier atomic dedup; the double-trade window is closed. Concurrent redelivery of one event could run its handler twice, and on the order path the handler is *route the order to the venue*. **Tier 1 (`pkg/bus`)**: `Deduper` was `Seen()`+`Record()` — a check-then-act, where two deliveries of one key both passed `Seen` before either `Record`ed. The split existed for a real reason (`Record` ran only after a *successful* dispatch, so a handler failure could not poison the window against retries), and a bare `SETNX` would have destroyed it: claim-and-never-release turns a failed handler into a **lost event**. The contract is now a three-phase lease that keeps both properties — `Claim` (atomic, one `SET NX EX` round-trip, exactly one concurrent winner), `Commit` (success ⇒ hold for the full window), `Release` (failure ⇒ the redelivery really does retry) — with a 5s lease so a worker that dies mid-dispatch has its claim expire rather than swallowing the event forever. Every consumer exit path commits or releases; Redis errors still fail OPEN. **Tier 2 (`services/oms`)**: the bus was never the only hole, and fixing it alone would not have closed this — bus dedup keys on `idempotency_key`, so a re-submit under a *fresh* event id is invisible to it. The OMS's own "idempotent re-submit" guard was `Load()`-then-`Save()`, the same check-then-act, and what runs immediately after it is `s.work()` → `router.Route()` → **the venue**. Two concurrent deliveries both saw `ErrNotFound`, both admitted, and both traded; the state converged (`Save` upserts) so it *looked* idempotent. `Store.Create` is now the atomic admission gate (`ErrExists` ⇒ ack and stop, before the venue). The sharedstate contract test tolerated 25% duplicate leakage on the grounds that idempotent handlers were the real guarantee — **both halves were false**; it now asserts exactly-once and is deterministic (10/10 under `-race`, where it previously leaked 33–60% and flapped). The OMS gained a *concurrent* resubmit test counting real venue executions — the existing idempotency test was sequential, which is why it passed while the bug was live.

### Phase 10 — Product surface (end-user client)

- **PS-02a** — the web BFF (`services/web-bff`): the browser front-of-house over the delivered `/v1` edge, the CLI's browser counterpart. It runs the OIDC authorization-code + PKCE login against Eighred SSO (`internal/oidc`: discovery, PKCE S256, authorize redirect, code exchange), holds the issued token in a server-side session keyed by an httpOnly cookie (`internal/session`: in-memory TTL default with a one-time PKCE-pending store for CSRF/state, clamped to token expiry), and reverse-proxies `/api/*` → gateway `/v1/*` with the server-held bearer attached — never forwarding the browser's cookie or exposing the token to JS. `/auth/login`, `/auth/callback`, `/auth/logout`, `/auth/me`, plus health/ready/metrics; stdlib `net/http`, mirroring the copilot/regulatory service shape. End-to-end tests drive login→callback→proxy and assert the security properties (bearer injected, cookie stripped, unauth 401, forged-state 400, one-time pending). Adds no auth endpoints and no backend analytics; the SSO must register the `kanz-web` client + this BFF's `redirect_uri`, and the gateway validates the JWT via the delivered OIDCAuthenticator.
- **CLI-02** — the `kanz` terminal binary (`cmd/kanz`): a Claude-Code-style REPL that completes the CLI-01 device flow, persists the token (0600, atomic, under `os.UserConfigDir`), renders the KANZ TERMINAL header, and drives turns over the delivered `/v1` edge — natural-language questions through `POST /v1/ask` (answer + citations + refusal/injection/ungrounded warnings) and slash commands (`/exposure`, `/measures`, `/scenario`) through the risk endpoints, plus `/login`/`/logout`/`/whoami`. Auto-runs the device flow on the first turn when no valid token is cached; the bearer is read through a closure so a mid-session `/login` is picked up live. Pure client — talks only to the running gateway (which validates the SSO token via the delivered OIDCAuthenticator); no backend, no mocks. Split into testable `config`/`tokenstore`/`gateway`/`repl` packages; the copilot `/v1/ask` is a single-JSON response (not a stream — the board's "streaming" phrasing was aspirational; ground truth won). Completes the CLI vertical.
- **CLI-01** — the kanz CLI is now an Eighred SSO relying party for the RFC 8628 device-authorization grant: new `pkg/deviceauth` (client-side counterpart to `pkg/auth`'s server-side JWKS validator) resolves the device + token endpoints from the issuer's OIDC discovery document, begins authorization, shows the user_code/verification URI via a caller callback, and polls the token endpoint honoring the server interval + `slow_down` back-off and the `device_code` expiry — returning the issued token for a caller to bearer against the gateway. Adds NO auth endpoints and holds NO keys; identity stays owned by Eighred SSO. Injectable clock/wait keep the poll-cadence + expiry tests deterministic and fast. Unblocks CLI-02.
