# KANZ BRAIN

> Living context doc. Last reconciled 2026-05-15 against the architecture docs and KANZ_TASKS.md.

## Current System Understanding
- Event system is foundation layer
- Risk engine consumes FACT events
- Go handles infra, Python handles inference

## Key Decisions
- Kafka + NATS hybrid architecture chosen
- Envelope-based event design required
- Causality tracking is mandatory
- Modular monolith core (Go) + isolated edge processes for market ingestion, AI inference, and batch compute
- Prediction layer is hybrid: async streaming path (default) + sync gRPC path for interactive calls, with circuit breaker + degraded fallback
- Envelope vs payload schemas are asymmetric: Envelope is additive-only forever (a constitution); payload schemas may break, via a new `vN` package + dual-write migration (EVT-06)
- Payload schemas hold full compatibility (backward + forward) within a package version; backward compat must hold for the full Kafka retention window because replay reads old logs with current code
- Two payload-version fields, not redundant: envelope `schema_version` (uint32) = major version, bumps only on a breaking change, == package `vN`; `payload_schema_ref` registry version bumps on every change incl. additive
- NATS JetStream provisioned as the live spine (EVT-08): one stream per domain (`{domain}.>`), file storage, R3, `limits` retention; retention tiered — 24h hot domains, 7d platform/data, 1h observability, 30d DLQ; 2m dedup window for broker-side idempotency keyed on envelope `idempotency_key`. Replay streams are per-run, not standing (EVT-20)
- Kafka provisioned as the durable log of record (EVT-09): 3-node KRaft cluster (no ZooKeeper), RF3 / min-ISR2, auto-create disabled — topics provisioned explicitly. Topic = `{domain}.{entity}`; retention tiered — 7d high-volume, 30d most FACT/COMMAND, infinite for `platform.model`; `.snapshot` + `platform.config` compacted; a `dlq.{name}` paired with every delete-policy event topic
- New shared proto package `common.v1` (EVT-10): foundational value types every payload schema reuses, owned by event-platform + architecture, evolves under envelope-grade additive-only discipline — prevents cross-domain proto dependencies (e.g. risk schemas importing market). First member: `Decimal` (exact base-10, `coefficient × 10^exponent`); `double` is banned for prices/sizes/money
- Market payload design (EVT-10): `MarketDataEvent` is self-contained (instrument identity + `event_time` inline) so events survive being pulled from a batch; `MarketDataBatch` is per-instrument — all events share one `instrument_id` = envelope `partition_key`, ordered by non-decreasing `event_time`, so per-partition ordering still holds
- Domain/state payload design (EVT-11): `PortfolioState`/`PositionState` are aggregate-level state payloads — portfolio does NOT embed positions (those are their own events); `PortfolioSnapshot` is the STATE_SNAPSHOT and carries a `LogPosition` for gap-free bootstrap; exposures are emitted as a coherent `ExposureSet`, never piecemeal. `common.v1` gained `Money` (Decimal + ISO 4217) and `LogPosition` (durable-log coordinate)
- Command layer design (EVT-12): `command.v1` is the generic command layer — what `envelope/v1` is to events. `CommandMetadata` (issuer, target, valid_until, reason) is embedded as field 1 by every concrete domain command; `command.v1` holds no domain-specific command body and no `Any` wrapper, so each concrete command keeps its own `payload_schema_ref` for clean registry tracking. `CommandOutcome` is the single universal outcome-FACT payload; the command it reports on is identified by envelope `causation_id`, not restated
- Payload timestamp convention (clarified EVT-13): a payload restates a domain timestamp only when events can be bundled under one envelope (batch/snapshot) so a single envelope `event_time` cannot represent them all — `MarketDataEvent.event_time`, `PositionState.as_of`. Standalone, never-bundled events (lifecycle FACTs) omit the timestamp; envelope `event_time` is authoritative. They still carry a principal (`*_by`) because envelope `source` is the emitting service, not the acting principal
- Observation payload design (EVT-14): general observations (`MetricObservation`, `DecisionLog`) are lossy-tolerant; `DataQualityEvent` is one schema with a `oneof` over gap/staleness/drift plus common triage fields (subject, severity, summary) so data-observability handles it generically, and it is FACT-grade despite `EVENT_CLASS_OBSERVATION` (the documented exception). Late data is an envelope `QualityFlag`, not a `DataQualityEvent` kind. `double` is fine for metrics and statistical drift scores — the exact-`Decimal` rule is specifically for money/prices/sizes
- Codegen pipeline (EVT-15a): generated code is never committed to `kanz-schemas` (gitignored, decided EVT-01). A tag-triggered `schema-release.yml` runs `buf generate` and publishes each language SDK as its own artifact. Go → companion module repo `github.com/kanz-eng/kanz-schemas-go`, committed + tagged by CI in lockstep with `kanz-schemas` releases. `.proto` files carry no `option go_package`; buf managed mode supplies it. Python (EVT-15b) and TS (EVT-15c) extend the same `buf.gen.yaml` + release workflow
- Python SDK (EVT-15b): uses buf.build **remote** plugins (`protocolbuffers/python` + `pyi` for stubs) — no clean standalone local plugin exists for Python, unlike Go. Published as the `kanz-schemas` package to a package index (PyPI or a private index via `PYPI_REPOSITORY_URL`), not a companion git repo. Package metadata is the versioned template `packaging/python/pyproject.toml`; CI injects the release version and adds the `__init__.py` files protoc-gen-python omits
- TypeScript SDK (EVT-15c): uses the buf-maintained `bufbuild/es` remote plugin (Protobuf-ES) with `target=js+dts` so the generated tree is ES modules + `.d.ts` declarations — no separate `tsc` step. Published as the scoped `@kanz-eng/kanz-schemas` package to npm (or a private registry via `NPM_REGISTRY_URL`); scope matches the `kanz-eng` org, `--access public` set so the scope still publishes openly. Template `packaging/ts/package.json` uses a wildcard `exports` map (`./*: ./*`) so consumers import per-file (`@kanz-eng/kanz-schemas/envelope/v1/envelope_pb.js`) without a hand-maintained barrel
- Go module layout (EVT-16a): single Go module rooted at `kanz/` (`github.com/kanz-eng/kanz`, Go 1.23), all services and shared packages live under it. Services are `package main` in `services/<name>/cmd/<name>/`; shared internal packages live under each service's `internal/` (per-service first, promote to top-level `kanz/internal/` or `kanz/pkg/` only when a second consumer appears). Stdlib `net/http` + `log/slog`; only direct external dep so far is `pgx/v5` for Postgres
- Schema registry storage (EVT-16a): one row per (`schema_id`, `version`) in Postgres `schemas` table — immutable once published per kanz-schemas/docs/schema-evolution.md §6. `Storage` interface (`Put` / `Get` / `Ping`); `Put` is idempotent — same `(ref, descriptor)` succeeds, different descriptor under existing ref returns `ErrConflict` (via `INSERT ... ON CONFLICT DO UPDATE SET source_tag = schemas.source_tag RETURNING fingerprint` to fetch the existing fingerprint in one round-trip). `descriptor` is opaque `BYTEA` — the registry doesn't decode it; format is the ingestor's contract (EVT-16b). Schema-ref wire form `<schema-id>:<version>` (e.g. `market.v1.MarketDataEvent:7`), parsed by `storage.ParseRef`. In-memory `Memory` backend ships alongside `Postgres` so the same test suite runs without a database
- Schema registry ingest (EVT-16b): the **registry assigns versions**, not the caller — `Storage.Register(schemaID, descriptor, sourceTag) → (Ref, created, err)` looks up the latest stored row for `schemaID`; same sha256 fingerprint ⇒ idempotent return of that ref with `created=false`; new content ⇒ insert at `latest+1` with `created=true`. Postgres impl uses a Serializable transaction since rare ingest correctness beats throughput. HTTP wire: `POST /schemas/{schema_id}` with raw FDS subset body + `X-Source-Tag` header; `200` vs `201` distinguishes idempotent from new. Per-message granularity is the *ingestor's* choice — the kanz-schemas tool slices the global FileDescriptorSet into one subset per top-level message (file + transitive imports), so each registry row is a self-contained FDS that `protoc --descriptor_set_in` can consume directly. Tool lives in `kanz-schemas/tools/registry-ingest/` as its own tiny Go module (only dep `google.golang.org/protobuf`) so kanz-schemas's CI doesn't pull in the kanz monorepo
- Schema registry resolve (EVT-16c): `GET /schemas/{ref}` — `ref` is the literal `payload_schema_ref` string (`<schema-id>:<version>`), placed unencoded in a single path segment since `:` is RFC-3986-legal there and Go's stdlib mux passes it through `r.PathValue` intact. Response body is the **raw descriptor bytes** (`application/octet-stream`), not JSON-with-base64 — descriptors are read on hot paths and base64 inflates by 33%. Metadata travels in `X-Schema-*` headers (`Fingerprint`, `Source-Tag`, `Created-At`) so consumers can read it without parsing the body. Because `(schema_id, version)` is immutable once published, responses ship `ETag: "<fingerprint>"` + `Cache-Control: public, max-age=31536000, immutable` — any HTTP cache, proxy, or client can hold the answer forever. Register also tightened: `schema_id` containing `:` now `400`s, keeping resolve URLs unambiguous
- Bus client foundation (EVT-17a): `kanz/pkg/bus` exposes a *single* `Client` interface (`Publish` + `Subscribe` + `Close`) implemented by both `NATSClient` and `KafkaClient` — EVT-17b–e (envelope stamping, trace propagation, dedup, DLQ) layer over either transport uniformly rather than reimplementing per backend. Library picks: `github.com/nats-io/nats.go` (JetStream v2 API) and `github.com/segmentio/kafka-go` (pure-Go, no cgo) — `kafka-go` chosen over `franz-go` and `confluent-kafka-go` because cgo-free builds matter for the kanz container images and 17a's needs are basic enough that the simpler API wins. Kafka writer pins `Hash` balancer (partition-by-key), `RequireAll`, `AllowAutoTopicCreation=false` (per EVT-09 the topics-job owns provisioning), and Snappy. Per-message manual commit on the Reader so EVT-17e can own retry/DLQ semantics without fighting auto-commit. `Message.Key` round-trips natively over Kafka; over NATS (no native key) it rides as a `Kanz-Partition-Key` header that the receive path strips from the user-visible `Headers` map. Handler returns nil ⇒ ack/commit; non-nil ⇒ nak (NATS) / skip-commit-redeliver (Kafka). Bus client does *not* manage streams or topics — those stay in `kanz/infra/{nats,kafka}/`
- Wire framing (EVT-17b): every bus message body is a serialized `envelope.v1.EventFrame { Envelope envelope = 1; bytes payload = 2 }`. Sibling layout (not nesting `bytes payload` inside `Envelope`) was chosen so payload-blind tooling — schema registry, observability, replay, routing — can decode the envelope without bringing in the payload schema. EventFrame lives in `envelope/v1` because the framing is a universal envelope-platform concern; adding it is non-breaking (new sibling message in the package, no Envelope change, no `envelope_version` bump per envelope-policy §6). Producer/Subscriber wrappers serialize/deserialize the frame; the underlying `Client` stays bytes-only
- Stamping + validation (EVT-17b): `Producer` over a `Client` owns the publish-side rules. Auto-stamped: `event_id` (UUIDv7, time-sortable), `publish_time` (now), `ingestion_time` (defaults to now), `correlation_id` (defaults to `event_id` on roots), `envelope_version` (constant `1` for now), `source` + `producer_version` (from `ProducerConfig`), `producer_sequence` (per-(event_type, partition_key) monotonic counter under a mutex — 0 when partition_key is empty), `idempotency_key` (= `event_id` for FACT/STATE_SNAPSHOT/OBSERVATION; caller-supplied for COMMAND, rejected if missing). `Validate` is exported and reusable on the consumer receive side; it enforces every required-field rule in envelope-policy §7 + the FACT idempotency invariant + the live-publish prohibition of `QUALITY_FLAG_REPLAYED` (replay sets this; live publishers must not). Caller-set `IdempotencyKey != event_id` on a non-COMMAND event is a stamping error, not silently overwritten. `Unframe` is the consumer-side helper
- Go module dependency on schemas (EVT-17b): `kanz` requires `github.com/kanz-eng/kanz-schemas-go` (the Go SDK published by `schema-release.yml`). Until the first kanz-schemas release tag, dev/CI use `replace github.com/kanz-eng/kanz-schemas-go => ../kanz-schemas/gen/go` after running `buf generate` + `go mod init` in `kanz-schemas/gen/go/`. The `replace` line is the marker to strip once a tagged release exists. New deps in `kanz/go.mod`: `google.golang.org/protobuf`, `google/uuid` (UUIDv7)
- Lineage propagation (EVT-17c): `correlation_id`, `causation_id`, `trace_context` ride `context.Context` between handler and downstream publish — not function parameters — so a typical "receive → do work → publish derived event" path threads lineage with zero hand-coding. Three unexported `ctxKey` slots populated by `bus.With{Correlation,Causation,Trace}…` helpers; `Consumer` stashes them automatically on receive. Key subtlety: `causation_id` stashed under the *next* event's slot is the **current** event's `event_id` (not the current event's `causation_id`) — that's how the chain links. Precedence on publish is **explicit Event field > ctx-derived > root default**: explicit values always win, so a producer that wants to break the chain (e.g. emit a true root event from inside a handler) just sets `Event.CorrelationID` explicitly. Empty `trace_context` is not stashed (avoids overwriting an existing ctx value with empty). `Consumer` also runs `Validate` on every inbound envelope — defense-in-depth and lets EVT-17e's DLQ catch malformed messages once it lands
- Dedup (EVT-17d): two reinforcing layers, not one. **Publish side** — Producer stamps `Nats-Msg-Id: <idempotency_key>` on every outbound `bus.Message`; NATS JetStream keys its broker-side dedup window on this header (EVT-08's 2m window). Kafka carries it as a regular user header (harmless). One header serves both transports because NATS reserves the name and Kafka is name-agnostic — the alternative of defining our own header and translating in NATSClient added complexity for no gain. **Consumer side** — bounded sliding `DedupWindow` keyed on `idempotency_key`, default 2m / 10k entries (TTL matches NATS so the layers reinforce: a duplicate that slips broker dedup is caught by consumer dedup; a duplicate within window is caught by either). Split API (`Seen` / `Record`) lets `Consumer.Subscribe` record **only after a successful dispatch** — a transient handler failure must remain retry-able. Two concurrent deliveries of the same key can both pass `Seen` before either `Record`s, so handlers must be idempotent (event-class-rules §1) — the window is a perf optimization, not a correctness primitive. Dedup is **per-instance, in-memory**; cross-pod dedup is explicitly out of scope (cross-pod redelivery is handled by idempotent handlers, not by sharing the window through a store). `NewDedupWindow(0, …)` or `(…, 0)` returns nil; methods are nil-safe so the disabled path needs no nil-checks at every call site. Eviction is lazy GC of expired entries first, then oldest-evict if still at capacity
- Retry + DLQ (EVT-17e): bounded retry happens **inside** the Consumer's dispatch — `RetryConfig.MaxAttempts` loop with exponential backoff (no jitter at this layer; capped at `MaxBackoff`; sleep is ctx-cancelable). Tradeoff: this blocks the partition for the retry sequence; high `MaxAttempts` × long backoff trades throughput for resilience. The alternative (retry by re-publishing to a delay topic) was rejected for 17e because it needs delay-queue infra Kafka doesn't have natively — revisit if partition stall becomes an operational issue. **DLQ subject convention**: `dlq.<original-subject>` (matches the `dlq.>` NATS stream and the `dlq.{name}` Kafka topics already provisioned in EVT-08/09). DLQ pre-dispatch failures (`Unframe`/`Validate`) are routed too, with `Kanz-DLQ-Attempts: 0` — payload was never run. Body and original headers (incl. `Nats-Msg-Id`) are passed through unchanged so investigators can re-parse the frame and DLQ consumers can dedup if they wish. Three load-bearing details: (1) DLQ publish failure surfaces — the broker re-holds the message, never lose poison events; (2) DLQ success records the idempotency_key in dedup so subsequent duplicates of the same poison skip (terminal); (3) `WithRetry` and `WithDLQ` are independent — DLQ-without-retry is "first failure is poison", retry-without-DLQ is "bounded attempts then surface to broker"
- EVT-17 epic complete: the Go bus client is end-to-end runnable as of EVT-17e — `Producer`+`Consumer` over either `NATSClient`/`KafkaClient` give a service the full stamp → validate → publish → subscribe → unframe → validate → dedup → retry → DLQ pipeline. Python (EVT-18) and TS (EVT-19) clients are next; they must match this contract on the wire (`EventFrame` framing, `Nats-Msg-Id` header semantics, dedup `idempotency_key`, DLQ subject prefix + `Kanz-DLQ-*` headers, ctx-style lineage propagation in whatever each language's idiom is)
- Python bus client foundation (EVT-18a): new `kanz-py/` tree, package name `kanz-bus` on PyPI, importable as `kanz_bus`. Async-first throughout — `nats-py` and `aiokafka` are both asyncio-native, so the public API is `async def`-everywhere with `async with` context-manager lifecycle and `asyncio.CancelledError` as the cancel signal (mirroring Go's ctx-cancellation). Kafka library pick: **aiokafka over confluent-kafka-python** — aiokafka is pure-Python (no librdkafka cgo dependency), single asyncio event loop, matches the rest of the Python stack; confluent-kafka offers higher perf but its thread-pool model fights asyncio and ships a C dependency. Wire compatibility with the Go client is the load-bearing constraint: `Message {subject, body, key, headers}` shape matches `bus.Message`; the same `Kanz-Partition-Key` header bridges `key` over NATS (since NATS has no native key) and is stripped on receive. NATS uses **pull-subscribe** with a fetch-loop (durable per (subject, group)) rather than callback-based push, so cancellation is clean — a timeout cycle lets `CancelledError` propagate quickly. Kafka uses per-Subscribe `AIOKafkaConsumer` (one consumer per call) with `enable_auto_commit=False` so EVT-18d can own retry/DLQ. Test layout: tests live in `kanz-py/tests/` (outside the package so they don't ship in the wheel); `asyncio_mode = "auto"` in pyproject means async test funcs don't need explicit decorators
- Python stamping + validation (EVT-18b): wire-identical to Go EVT-17b — same `envelope.v1.EventFrame` framing, same `Nats-Msg-Id` broker-dedup header, same per-(event_type, partition_key) monotonic `producer_sequence`, same `idempotency_key` derivation rules per event class. `Producer` is sync-safe within a single asyncio event loop without a lock: `_next_sequence` is a regular method, no `await` inside, so its dict read-modify-write is atomic under asyncio's cooperative scheduling — adding `asyncio.Lock` would be ceremonial. **UUIDv7 implemented inline** (~10 lines bit-packing) rather than pulling in `uuid_utils` or `uuid-extensions`: stdlib `uuid.uuid7` arrives in Python 3.13 but the package floor is 3.10, and the inline implementation matches RFC 9562 exactly. `validate(env)` raises `ValueError` (Python idiom) where Go returns error — same rules, same error messages where practical for cross-language log grepping. **kanz-schemas Python SDK dep**: pyproject declares `kanz-schemas>=0.1.0`; until the first release, dev uses `pip install -e ../kanz-schemas/gen/python/` after `buf generate` (analogue of the Go `replace` directive). `protobuf>=5.29` pinned to match the schema-release CI's generated-code expectations
- Python lineage propagation (EVT-18c): the Python idiom for "thread something across `await` boundaries without an explicit parameter" is `contextvars.ContextVar` (PEP 567) — asyncio copies the Context across await within a coroutine and snapshots into newly-created tasks, so propagation just works. Three module-level contextvars in `kanz_bus.propagation`; primary API is a `@contextmanager` `propagation_context(*, correlation_id, causation_id, trace_context)` that sets only non-empty fields (empty values must not clobber an outer-context value — same "non-empty only" rule as Go's `WithTraceContext` skip on empty). **`EventHandler` deliberately has no explicit ctx arg** — `Callable[[Envelope, bytes], Awaitable[None]]`. Lineage is implicit. This is the right Python idiom but trades the Go ergonomic of "look at the function signature to see what's threaded"; the README and module docstring make the implicit threading explicit. `Producer.stamp` precedence stays the same as Go: explicit `Event` field > contextvar > root default. Same load-bearing subtlety: the `causation_id` stashed for the *next* event is the **current** event's `event_id` (not its causation_id) — that's how the lineage chain links
- Python dedup + retry + DLQ (EVT-18d): the Python plan **combined** what Go split into EVT-17d (dedup) and EVT-17e (retry+DLQ) into one subtask — same underlying behaviour, less ceremony. `DedupWindow` uses a "disabled-mode instance" instead of nil (Python's analog of Go's nil-safe receiver) — pass `DedupWindow(ttl_seconds=0)` to get a no-op instance, so `Consumer` always has a usable `_dedup` reference and never needs to nil-check. `RetryConfig` uses a dataclass with sensible defaults plus a fallback on the `backoff()` method for zero-field-value cases. `ConsumerConfig` is a single dataclass holding the three independent options (`dedup_window`, `retry`, `dlq`) rather than functional-option-style — more idiomatic Python and discoverable in IDEs. **`asyncio.CancelledError` is re-raised** out of the retry loop without being swallowed by `except Exception` — critical for the broker shutdown path. Same Go-side wire contract: `Nats-Msg-Id` header for broker dedup (set in Producer, EVT-18b), `dlq.<subject>` topic convention, `Kanz-DLQ-{Original-Subject,Attempts,Error}` headers. EVT-18 epic complete: the Python client is now end-to-end runnable, wire-compatible with Go EVT-17, and reading the same envelope frames the schema-release pipeline publishes

## Assumptions
- Interactive (sync) inference path target <50ms — percentile (p50/p99) TBD; async streaming path has no 50ms bound
- Per-partition event ordering preserved (partition_key + producer_sequence); no global ordering guarantee
- All state changes must be event-driven

## Open Questions
- How to handle cross-region event replication?
- Is the <50ms interactive inference target measured at p50 or p99?

## Anti-Decisions (important)
- No microservices sprawl before the domain is understood
- No single undifferentiated backend process — market ingestion, inference, and batch compute must be process-isolated
- No polling-based architecture
- No silent failure handling
