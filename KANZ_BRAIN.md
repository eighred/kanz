## Strategic direction — automated execution system (repositioned 2026-07)

> This is the current identity of the system and reframes everything below it. The sections after this one (System shape, Event platform, Persistence, Security, Analytics…) describe the **underlying platform substrate** — the event spine, bitemporal journals, multi-tenancy, and the risk/accounting/regulatory analytics. That substrate is retained and load-bearing, but it is no longer the client surface.

- **Kanz is an Automated Fund-Management & Multi-Exchange Execution System.** The analytics/Aladdin-class platform became the valuation/risk substrate underneath a trading loop; the client surface is the automated loop, not the analytics API. The CLI/web product surface (PS-0x) is **parked** behind this direction.
- **The loop:** proprietary TradingView Pine strategies → HMAC-authenticated webhook → `signal.v1.StrategySignal` FACT (advisory) → venue-allocated `order.v1.SubmitOrder` COMMANDS → simultaneous multi-venue (Binance/OKX) execution → bitemporal FACT-folding projection (`tv-sync`) → TradingView Broker-API feedback. Every hop is on the delivered event spine; nothing bypasses it.
- **A signal is advisory intent, never a command.** `services/webhook-ingest` validates it (HMAC over the raw body = the perimeter boundary, IP allowlist, nonce-replay window), records the immutable `StrategySignal` FACT (the audit root everything chains causation to), then fans out the concrete order COMMANDS the OMS's pre-trade compliance/risk gates still apply to. Treating the signal as a command would skip those gates. Command issuer = `strategy:{id}`; that path runs no `VerifyCommandIssuer` because HMAC is its authority boundary. **Reuse-first:** webhook-ingest is a command producer like the gateway; the OMS is the unchanged execution engine — no parallel execution path.
- **`SizeType` enum day 1** (ABSOLUTE_QTY / PCT_OF_EQUITY / QUOTE_NOTIONAL): institutional strategies rarely signal absolute units, so the translator resolves size against live NAV/mark from the accounting + position projections. Leverage + `MarginMode` are present day 1 (leverage-ready) but Phase 1 executes **spot-only**, isolating liquidation logic from bring-up bugs. Signal provenance is first-class (`SignalSource`: TRADINGVIEW_WEBHOOK vs NATIVE_ENGINE) — Kanz is a **hybrid brain** (external strategies + native alpha); provenance is never inferred from the subject or `strategy_id`.

### Multi-venue execution seam

- **`execution.Venue` seam** (`MIC()`, `Execute`) + a **venue-aware Router** (the allocation matrix) + a `venue` field on `SubmitOrder`/`OrderState` = the multi-venue allocation matrix. The Router sends each fanned-out order to the venue whose MIC matches; empty ⇒ smart-order-routing default. This is the same seam-the-vendor discipline as the analytics vendor SDKs.
- **Per-venue build-tag connectors** (`//go:build binance`, `//go:build okx`, shared infra under `binance || okx`; interfaces untagged). The **default binary is vendor-free** — it links no `coder/websocket` (verified via `go list -deps`); the authorized websocket transport links only under an exchange tag. Same build-tag-composition-root split as `-tags anthropic`/`-tags redis`.
- **Deterministic exchange-side idempotency:** our `order_id` *is* the venue `clOrdId` / `newClientOrderId`, so a duplicate or ambiguous-timeout submit recovers by querying that id rather than double-executing. `fill_id` is deterministic (`{venueSymbol}-{tradeId}`) so the synchronous `Execute` path and the asynchronous user-data-websocket echo of the same fill dedup to one.
- **The exchange is the source of truth; reconcilers never edit state.** Two audit layers — the user-data websocket (primary) and a periodic REST reconciliation loop (secondary) — emit **correcting FACTs** (`order.v1.StateHealed`, `accounting.v1.BalanceReconciled`) carrying venue truth with `QUALITY_FLAG_REVISED`; the journal/projection fold them to restore parity. **Never fabricate a fill:** a rate-limited or failed poll degrades (skips the tick), it does not invent an execution. A **DNS-bypass dialer** keeps the live path off blocking DNS.
- **In-Flight Certainty (the healing seam).** A close (cancel / IOC market flatten) races the venue and its ack can hang. A close unconfirmed past a hard **1500 ms** timeout is force-resolved by a fast reconciler watchdog: query by `clOrdId` → adopt venue truth if terminal, else **force-clear** (`StateHealed`→CANCELLED) and **sweep** the residual exposure with an aggressive market order (idempotent `heal-`+id `clOrdId`, never double-flattens), then re-anchor balances from real venue truth. **The ledger must never freeze**; the sweep's real fills arrive via the stream, never fabricated. The `CloseIntent`/`PendingCloses`/`CloseTracker` seam is untagged (shared across venues, one process-wide `CloseRegistry` written by the OMS and drained by whichever venue watchdogs are compiled in); the in-memory `CloseRegistry` is the default. A retry preserves the original timeout clock so back-off never resets it.
- **A close must reach the exchange, not just the ledger.** `Closer` is an *optional* `Venue` capability (`CancelOrder`, addressed by our deterministic `clOrdId`); the OMS type-asserts it and dispatches a real venue-side withdrawal before recording the cancellation. A venue with nothing resting externally (`SimVenue`) does not implement it and cancels ledger-only. The OMS **Tracks the close before it dispatches** — the window the seam exists to cover is exactly the hung call / ambiguous timeout / process death mid-flight, which a post-ack Track would miss. A venue error is never read as a successful cancel (a venue "order does not exist / already done" code *is* success — the order is not working); an unconfirmed cancel stays tracked for the watchdog and **does not nack the command**, because redelivering a cancel the venue may already have applied would freeze the ledger on an unresponsive exchange.
- **Only a close that leaves exposure open is swept.** Flattening a position (IOC market close) that fails leaves us still exposed ⇒ sweep the unfilled remainder. Cancelling a *resting* order does not: it never traded, so withdrawing it opens nothing, and a sweep there would **fabricate a brand-new position in the opposite direction** — the precise failure the degrade-not-fabricate rule forbids. So the cancel path Tracks a `CloseIntent` with no `SweepSide`/`Leaves` and the watchdog force-clears without sweeping. If a cancel raced a fill, the watchdog's venue query returns the order terminal and `StateHealed` carries that truth: we *learn* the fill, we never invent an offsetting trade.

### Off-bus hot path & native alpha

- **Raw L2 depth never rides the bus at full rate.** `services/market-ingest` (a process-isolated edge) folds the full-rate exchange depth feed into an in-memory `book.Book` and publishes **only bounded periodic `market.v1.OrderBookSnapshot`s** (for durable replay, cross-node bootstrap, audit) — plus, later, the native engines' signals. Depth carries a strict sequence chain (`prev_update_sequence`); a gap **re-snapshots** rather than folding out of order. This is the "market ingestion stays process-isolated" anti-decision made concrete for crypto L2.
- **Re-anchor, never fold out of order — the source owns resequencing.** A `DepthSource` normalizes each venue's native sequencing onto one transport-neutral rule the book checks (`prev_update_sequence == book.lastSeq`), and on any break it re-anchors instead of emitting a delta the book cannot chain. Binance has no `prevUpdateId` on spot, so the source implements the venue's documented procedure (open the stream first, fetch the REST depth anchor, drop events with `u <= lastUpdateId`, require the first applied event to STRADDLE the anchor `U <= lastUpdateId+1 <= u`, then require exact `U == prev u + 1`); OKX carries a native `seqId`/`prevSeqId` chain, pushes its own snapshot on subscribe, signals "no change" by repeating `seqId`, and re-anchors by resubscribing. A silently mis-folded book prices every downstream decision wrong, so a gap is always a re-snapshot — never a guess.
- **Depth is public market data.** The market-ingest venue feeds carry **no API key or secret**, unlike the OMS connectors — the edge is read-only market ingestion. One book + engine per instrument **per venue**; books are never merged across venues (that is the arbitrage engines' job, over the read-seam). A build carrying both exchange tags therefore folds two independent books per instrument.
- **`internal/exchange/netdial`** holds the DNS-bypass dialer, promoted out of the OMS on the second-consumer trigger (market-ingest's depth websockets). It is untagged and stdlib-only, so sharing it puts **no vendor dependency in the default binary** — the websocket stays behind the per-venue tags. Its websocket client has a **zero `Timeout`** on purpose: `coder/websocket` rejects a client with one, and that timeout would apply to the whole long-lived stream rather than the handshake. Cancellation is always the caller's `ctx`.
- **Proprietary alpha math is isolated in a separate, restricted composition-root layer** (house rule). The OBI / cross-venue-arbitrage quantitative strategy files do **not** live in the open micro-service repos (`oms`, `tv-sync`, `webhook-ingest`, `market-ingest`). market-ingest owns only the book **read-seam** + a native-signal **emit port**; the math is consumed from the restricted layer.
- **`pkg/alpha` is that boundary, and the dependency runs private → public.** The restricted layer is a **separate Go module that imports `kanz/pkg/alpha`** and builds its **own edge binary**; kanz never imports it, so `kanz/go.mod` carries no private `require` and the open repo still builds for everyone. `pkg/alpha` exposes `MarketView` (the read-seam: best bid/ask, top-N depth, windowed aggressive buy/sell volume, last price — raw state, **no derived indicators**), `Engine` (what the restricted layer implements), `Intent`, and `Runner` (owns the edge: folds depth + trades, publishes the bounded snapshots, ticks the engines). Kanz's own `market-ingest` runs **the same Runner with zero engines** — it folds, it snapshots, and it decides nothing — so the code that touches the market is identical in both binaries and only the decision-making differs.
- **The engine must run in-process, which is why `pkg/alpha` is public and the edge is not.** An engine reading the book over the network would be reading the bounded periodic snapshot and would lose exactly the per-tick latency it exists for. `pkg/alpha` (public) *may* import `kanz/internal/...` because it is inside the kanz module; an external module may not. So the edge internals (`internal/marketedge/{book,depth,trades,ingest}`) stay internal and are **re-exported from `pkg/alpha` as type aliases** (`DepthSource`, `DepthUpdate`, `TradeSource`, `Trade`, `TradeSide`) plus feed constructors. Without those aliases the restricted layer could reference `alpha.Feed` but could never *name* the type of its `Depth` field — the boundary would compile and be useless. Verified from a real external module: its only direct kanz import is `pkg/alpha`.
- **One execution path, both brains.** `internal/signal/translate` is the single signal→orders translator, shared by `webhook-ingest` (TradingView) and `pkg/alpha` (native). **Publishing the `StrategySignal` FACT executes nothing — nothing subscribes to it**; it is the audit root. The *commands* trade. So the translator does both: record the FACT, then fan out the venue-allocated `order.v1.SubmitOrder` COMMANDs the OMS still gates. A second fan-out for native alpha would have been a second execution path that the pre-trade compliance/risk gates could drift away from.
- **An arbitrage leg must be IOC.** The two legs of a cross-venue arb are market-neutral only *together*: if one fills and the other rests unfilled, the hedge is gone and what remains is naked directional exposure at the exact moment the strategy believes itself flat. `Intent.TimeInForce` therefore rides through the translator to every leg; it defaults to DAY (correct for a directional signal, **wrong** for an arb leg), so an arbitrage engine must set IOC explicitly.
- **Volume delta needs the trade tape, not the book.** L2 depth says what is *resting*; a level shrinking could equally be a cancel or a fill, and only the trade stream says which. So the edge folds a second in-memory structure — `trades.Tape`, bounded by a **time** window (a count-bounded tape silently changes its horizon with market activity, meaning something different in a quiet market than a volatile one — precisely when the number matters). Volume is attributed by **aggressor (taker)** side; Binance's `m` flag reports the *buyer as maker*, so `m == true` means a taker **SELL** — reading it as "was a buy" inverts the sign of every signal built on it. An unreported aggressor counts to **neither** side, never guessed into a direction.
- **Sequencing decision:** OKX + the allocation matrix (M4) land **before** native alpha engines — never build HFT/alpha on un-reconciled execution paths. K8s node affinity Tokyo/London for exchange latency.

### State feedback (`tv-sync`)

- `tv-sync` is a **bitemporal FACT-folding projection + TradingView Broker-API** (REST + streaming), **zero-truth** (it derives everything from folded FACTs, holds no independent state), multi-tenant isolated, with average-cost realized/unrealized P&L. Live unrealized P&L folds a **MarkSource** bound to the venues' ticker feeds — universal market fact, not tenant-scoped.

### Production IP / perimeter security

- **Production binary stripping** (`-trimpath -ldflags="-s -w"`, the Makefile `release` target) resists decompilation of the proprietary execution logic (verified: `go tool nm` → no symbols). The default binary stays vendor-free.
- **Memory-only secrets:** exchange API keys / passphrases are fetched at runtime into RAM via env or mock-Vault `*_FILE` (CSI) mounts — never on disk, in Git, or in the stripped binary.
- **Egress-IP binding:** production keys are locked to dedicated Tokyo/London egress IPs. A 401/403 at the venue auth boundary is typed `ErrEgressDenied` — a **non-retryable structural fault** distinct from a transient 5xx or local rate-limit — so a deployment from an unauthorized environment fails loud instead of retrying into an exchange ban.

## System shape

- **Modular monolith core (Go) + process-isolated edges.** One Go module rooted at `kanz/` (`github.com/kanz-eng/kanz`, Go 1.23); services are `package main` under `services/<name>/cmd/<name>/`. Market ingestion, AI inference, and batch compute run as isolated edge processes — never folded into one undifferentiated backend. Shared code starts per-service in `internal/`, promoted to top-level `kanz/internal/` or `kanz/pkg/` only when a second consumer appears. Stdlib `net/http` + `log/slog` by default.
- **Prediction layer is hybrid:** async streaming path (default) + a sync gRPC path for interactive calls, with a circuit breaker + degraded fallback. Interactive target <50ms (async path unbounded); the p50/p99 split is a LATENCY-01 concern.
- **Everything is event-driven.** All state changes flow through events; there is no polling architecture.

## Event platform

- **Kafka + NATS hybrid, by role.** NATS JetStream is the live spine (short-retention hot tier — one stream per domain, tiered retention, 2m broker-side dedup keyed on `idempotency_key`). Kafka is the durable log of record (KRaft, RF3/min-ISR2, explicit topic provisioning, tiered retention with `platform.model` infinite, compacted `.snapshot`/`platform.config`, a paired `dlq.{name}` per delete-policy topic). **NATS is not a system of record** — DR rebuilds it from the Kafka log rather than replicating it.
  - **Kafka is DERIVED from NATS by ONE archiver. Services never dual-publish** (decided 2026-07-14, SHIPPED 2026-07-15 as DATA-M1 — `services/archiver`). A producer that writes to both transports is two writes that can partially fail, and a partial failure MANUFACTURES precisely the NATS↔Kafka divergence `internal/integrity` (DATA-05) exists to detect — the system would generate its own corruption and then congratulate itself for noticing. One writer means one place that can fail, one lag metric, and one write on the hot path. The archiver acks NATS only after Kafka acknowledges, so the failure mode is redelivery (at-least-once, `event_id` the dedup key), never silent loss. A structurally-unmappable event (bad `event_type`, cross-tenant, reserved prefix) is dead-lettered to `dlq.archiver` and acked, not retried forever. **Consequence, resolved:** Kafka is derived rather than independent, so DATA-05's two-transport premise no longer held — and the detector was DELETED rather than wired (DATA-M4, 2026-07-16; see *Data integrity* below).
  - **The archiver's contract is DURABILITY + LOCALITY, not Kafka-partition-position order** (decided 2026-07-15). Nothing is lost (ack only after Kafka acknowledges), and same `partition_key` ⇒ same partition, so a consumer *can* order. But across a sustained outage the repeated NAKs are re-scheduled by JetStream out of order — server-side, not fixable from the client — so partition POSITION is not a total order. The authoritative per-key order is carried in the event: `producer_sequence` (monotonic *per producer* — a per-key total order only where one service owns an entity's events; across producers to one key, fall back to `event_time`/causal fields). Order-dependent consumers (DR rebuild, replay) reconstruct order from those, never from Kafka partition position.
  - **Bus consumers `Drain()` on shutdown, not `Stop()`** (fixed 2026-07-15, `pkg/bus/nats.go`). `jetstream.ConsumeContext.Stop()` DISCARDS buffered-but-undelivered messages; JetStream starts a message's `AckWait` at FETCH time, so `Stop()` stranded in-flight messages server-side for a full 30s while their NACKed siblings redelivered first — reordering any durable consumer's output on an ORDINARY restart, fleet-wide (tv-sync's order-dependent fold included). `Drain()` runs buffered messages through the callback first, under a fresh bounded context (NOT the cancelled shutdown ctx — that would fail every downstream publish and NACK the very messages being drained); anything unhandled at the grace deadline is NACKed for immediate redelivery.
- **Envelope vs payload asymmetry.** The envelope is additive-only forever — a constitution, never a breaking change, no `envelope_version` bump for new sibling messages. Payload schemas may break, via a new `vN` package + dual-write migration. Payload backward-compat must hold for the full Kafka retention window, because replay reads old logs with current code.
- **Two version fields, not redundant:** envelope `schema_version` (major, bumps only on a break, == package `vN`) vs the registry `payload_schema_ref` version (bumps on every change including additive).
- **Wire framing:** every bus body is a serialized `envelope.v1.EventFrame{ envelope = 1; bytes payload = 2 }`. Sibling layout (not payload-nested-in-envelope) so payload-blind tooling — registry, observability, replay, routing — decodes the envelope without the payload schema.
- **`common.v1` shared value types** (Decimal, Money, LogPosition) exist to prevent cross-domain proto dependencies (e.g. risk importing market). **`Decimal` is exact base-10; `double` is banned for money/prices/sizes** (fine for metrics + statistical scores). Exact money/qty never touch float anywhere — serialized losslessly as `*big.Rat` RatString. The single implementation of that rule is **`internal/dec`**, consolidated at Milestone 5 from five identical service-local copies (oms, webhook-ingest, market-ingest, accounting, tv-sync) that each exported a different subset of the same functions: identical `Decimal`↔`big.Rat` semantics on every hop are what keep the guarantee intact end to end, and five copies were five chances for them to drift.
- **Command layer:** `command.v1` is generic (a `CommandMetadata` embedded as field 1 by every concrete command; no `Any` wrapper, so each command keeps its own `payload_schema_ref`). `CommandOutcome` is the single universal outcome-FACT, linked to its command by envelope `causation_id`.
- **Codegen: generated code is never committed to `kanz-schemas`** (gitignored). A tag-triggered `schema-release.yml` runs `buf generate` and publishes each language SDK as its own artifact — Go → companion module repo `kanz-schemas-go`, Python → package index, TS → npm `@kanz-eng/kanz-schemas`. `.proto` carry no `option go_package`; buf managed mode supplies it. A CI guard rejects any tracked generated file.
- **Load-bearing dev seam:** `replace github.com/kanz-eng/kanz-schemas-go => ../kanz-schemas/gen/go` (+ Py/TS equivalents) until the first published release tag. This is the marker DEBT-01/PARITY-07 strips; it is correct and load-bearing until a publish target exists.
- **Schema registry:** the registry assigns versions (not the caller); a `(schema_id, version)` row is immutable once published. Ref wire form `<schema-id>:<version>`; resolve returns raw descriptor bytes (not base64-JSON) with immutable cache headers; an in-memory backend ships beside Postgres so the same suite runs without a DB.
- **Bus client:** a single `Client` interface (`Publish`/`Subscribe`/`Close`) over both `NATSClient` and `KafkaClient`, so envelope stamping / lineage / dedup / DLQ layer once. Libs: `nats.go` + `segmentio/kafka-go` — kafka-go chosen cgo-free because the container images are distroless. The bus client manages neither streams nor topics (those live in `infra/{nats,kafka}/`).
- **Lineage rides the language's implicit-context mechanism, not parameters:** Go `context.Context`, Python `contextvars`, TS `AsyncLocalStorage`. Load-bearing subtlety: the `causation_id` stashed for the *next* event is the *current* event's `event_id` — that is how the chain links. Empty values never clobber an outer context.
- **Dedup is a performance optimization, not a correctness primitive.** Two reinforcing layers (broker `Nats-Msg-Id` window + a per-instance consumer window); it is per-instance and in-memory. Cross-pod correctness rests on **idempotent handlers**, always. Retry + DLQ live inside the consumer's dispatch; DLQ subject = `dlq.<original>`, with pass-through headers so investigators can re-parse.
- **Cross-language clients (Go/Py/TS) must match on the wire:** EventFrame framing, `Nats-Msg-Id` broker-dedup semantics, `idempotency_key` dedup, `dlq.<subject>` + `Kanz-DLQ-*` headers, per-(event_type, partition_key) monotonic `producer_sequence`, and the same lineage chain — each expressed in its language's idiom.
- **Replay isolation is source-side first.** The Kafka replay reader uses **no consumer-group** (direct partition reads mutate no live consumer's offsets) — the primitive that makes replay safe even before namespacing. Republished events land under `replay.{runID}.*` + a `replay-{runID}` group and are stamped `QUALITY_FLAG_REPLAYED`. Validation is bidirectional: live validators hard-reject REPLAYED (route to DLQ, loud); replay-scoped validators require it. Stamping is owned by the replay Pipeline, not the Producer (which would clobber `event_id`/`producer_sequence`).
- **Replay is a snapshot of history, never a tail — and a Kafka time bound must be compared at Kafka's own resolution (DATA-M6, 2026-07-17).** Two independent traps in `tools/replay.Reader`, found by instrumenting every returned event rather than guessing: (1) Kafka message timestamps are **millisecond-resolution on the wire**; a caller's `time.Time` bound routinely is not. A message whose true time exactly equals an exclusive `EndTime` round-trips through Kafka truncated to whole milliseconds and comes back strictly *before* the untruncated bound — the exclusive check then fails to exclude the very event it was built to exclude. **Any code comparing a fetched Kafka message's timestamp against a caller-supplied bound must truncate both to millisecond resolution first**, or boundary events compare wrong in a way that is bit-for-bit reproducible, not flaky. (2) A range's end bound (offset or time) describes the *request*, not *reality*: `FetchMessage` blocks for a message that satisfies the bound, and on a range beyond the log's current end no such message will ever arrive — a DR restore that never returns is useless. The fix is to probe each partition's high-water mark once, at seek time, and stop at `min(EndOffset, HWM-1)` regardless of which bound the caller gave. **Both defects were latent for two days behind a CI gate nobody read**, not because the gate was silent — `d121875` had just made these tests stop skipping specifically so this couldn't happen — but because a red `main` on a Kafka-gated suite did not, by itself, stop 96 commits from landing on top of it.

## Data integrity

- **`internal/integrity` (DATA-05) was DELETED, not wired (DATA-M4, 2026-07-16) — and it is the worked example of a speculative abstraction losing to the code it was built for.** It held a detect-then-emit data-quality layer: gap / staleness / watermark-late / drift classifiers, a `Publisher` emitting `DataQualityEvent`s, `Mark*` helpers stamping envelope `quality_flags`, and a NATS↔Kafka divergence `Reconciler` with a Redis Lua `PendingStore`. **Every line of it was unreachable.** `go list -deps ./services/... ./cmd/...` never resolved it; it entered the graph only under `-tags redis`, through one compile-time assertion (`_ integrity.RedisEval`) in `pkg/redisadapter` for a store nothing constructed. **Three independent forces killed it, and each is the general lesson:**
  - **Its premise expired.** The `Reconciler` policed divergence between two independent transports. DATA-M1 made Kafka DERIVED from NATS by one archiver that acks only after Kafka acknowledges — so there is no second writer to diverge from, and a detector for an impossible fault is not a safety net, it is false assurance waiting for whoever wires it. **When a foundational decision removes a component's reason to exist, DELETE the component in the same breath — a design that outlives its premise is read by the next engineer as a requirement.**
  - **Its intended consumers rejected it in writing.** The two services that actually do data-quality work — `datamaster/internal/pricing` and `market-data/internal/feed/dq` — each wrote their own and left a comment explaining that integrity's detectors are *envelope/stream-bound* and theirs must run on a pre-publish payload. The abstraction was pitched one layer above where the work happens. **A shared layer nobody imports is not "ready for its second consumer": the second consumer already came, looked, and wrote their own.**
  - **It duplicated live behaviour.** `flags.go` wrapped `quality_flags` stamping while ten production files (`pkg/bus/producer.go`, `validate.go`, the venue reconcilers' `QUALITY_FLAG_REVISED`, `risk/degraded.go`) did it inline — the competing abstraction this repo forbids, sitting unused beside the real one.
  - **The retired rule, kept for the record:** flags belonged in the integrity layer and never in `bus.Producer`, so the generic transport would not depend on integrity. With integrity gone the inversion it guarded against cannot occur; `bus` stamps flags directly and that is now simply where it lives.
  - **It survived one forge pass by being well-commented.** A 2026-07-15 pass "disproved" the deletion candidate with `grep -l internal/integrity` and reported three live importers — two of which were the very comments above, saying the package was *not* used. **A claim about the dependency graph is the compiler's to answer (`go list -deps`), never grep's:** on a codebase that documents what it declined to use, a file grep over-reports exactly the dead code the pass exists to find.

- **THE PRE-TRADE GATE REFUSES TO EVALUATE WHAT IT CANNOT VALUE (COMP-M1, decided 2026-07-16, lead).** An order with no usable price — nil, zero, or negative — is refused as `Unpriced` before `project()` runs. It is a terminal rejection under its own code (`PRICE_UNAVAILABLE`), never an `error` and never a rule violation, because nothing was breached: nothing was *checked*. **Consequence, and it is a live behaviour change, not an internal detail: MARKET and STOP orders against a governed portfolio holding ≥1 rule are now REJECTED**, because a `SubmitOrder` carries only a limit price. COMP-M2 (wire a reference-price source) is what admits them again. **Rejected alternative:** wire the price source first and keep evaluating meanwhile — refused because it inverts the default. A gate that will value an unpriced order at zero is unsafe *by construction*; the price source is a feature, and its absence must not be a silent bypass. An unconstrained mandate (zero rules) still admits unpriced orders: no evaluation occurs, so there is nothing to protect.
  - **What it fixed: every market order bypassed every rule, and had since the gate shipped.** A nil price projected the position at zero market value (`gate.go` `mulDecimal(qty, nil) == 0`); `project()` **replaces** the traded position, so the zero overwrote the real value loaded from the book; and `heldPositions` (`rules.go`) skips zero-value positions — draining Concentration, Restriction, IssuerExclusion, Currency and Leverage, the entire rule set. A market order touching an **already-breaching** holding erased that breach from its own check. The only backstop was the post-trade monitor, which fires after execution.
  - **It is the EXEC-M14 collapse, one door over — in the same file.** `Evaluate` already carries the lesson in prose: *"TWO DIFFERENT STATES, and collapsing them is what made this silent"* (no mandate vs. a mandate constraining nothing). `heldPositions` collapsed **"quantity is zero, so it cannot breach"** (true) with **"price is unknown"** (not remotely true), and the two became one observable event. **Finding a collapse and fixing it in one place is not finishing: the same shape recurs wherever a sentinel value carries two meanings.** Zero is the most overloaded sentinel there is.
  - **The invariant lives at the choke point because a second door already existed.** `services/optimization/internal/bridge` leaves the price nil whenever an instrument is absent from its `prices` map — the rebalancer had the identical bypass, reached by a different caller. Enforcing in the OMS adapter would have fixed one and left the other, which is this repo's signature defect. **Both callers of `PreTradeGate.Evaluate` pass through `Evaluate`; that is where the refusal belongs.**
  - **A false comment is worse than no comment, and this one is why the bug survived review.** `comp01.go` documented the zero-value projection as "a known v1 gap" and asserted *"the existing book is still fully checked"*. The first half was true and made the second half credible. The second half was false — the traded instrument, precisely the one under scrutiny, went blind. **A comment that reassures is load-bearing: it is what the next reviewer checks instead of the code.** It was deleted, not amended.

## Cross-cutting engineering patterns

_These are the recurring disciplines the whole codebase is built on — the most reusable knowledge here._

- **Seam-the-vendor.** Every external dependency (vendor SDK, protocol, broker/DB binding) sits behind a delivered, narrow interface; the concrete binding wires at the composition root (`cmd/*`). The vendor SDK is itself the seam — the core module carries no vendor import.
- **Build-tag composition-root split.** When the composition root is *in* the module (e.g. `cmd/copilot`), importing a vendor SDK there still bloats `go.mod` — so split `//go:build` files (`model_stub.go` default vs `model_anthropic.go`; `redisadapter` behind `-tags redis`). The default build stays dependency-free; prod builds with the tag.
- **Degrade-not-fabricate.** On an external failure (Redis outage, lineage 403/404, garbage calibration inputs) degrade to the safe/no-op answer — never invent a result. Authorization and promotion gates are deny-by-default.
- **Generated-not-committed decoder seam.** For schemas not yet in `gen/go` (`settlement.v1`, `alternatives.v1`, `wealth.v1`), payload decode/encode is a `Decoder`/`Encoder` seam (default JSON over the Go-native type; the proto binding wires when the SDK generates) — the same stance as the codegen decision, applied to consumers.
- **The in-memory default *is* the test seam.** Every durable `Store` keeps its in-memory implementation beside the Postgres one, with identical fold/replay semantics; DB-backed tests are gated on `TEST_POSTGRES_URL` and skip without a database.
- **Import-boundary discipline, enforced by an arch test.** E.g. `curve`/`volsurface` cannot import `compute`, so the compile-time `Provider` assertions live in `compute`; a `factor`→`compute` cycle is avoided with closures.

## Persistence & durability

- **Event-sourced journals with bitemporal reads** (`effective_time`, `knowledge_time`, entry_id), idempotent append on the entry PK. Postgres behind every Store, RLS-scoped by the `app.tenant_id` GUC, deny-by-default tenant isolation. **Snapshot + tail-replay == full replay** is the determinism contract, enforced per-store (the Go internal-package boundary forbids a central cross-service importer). PITR + cross-region warm standbys via CloudNativePG.
- **A read model is served from its store, and a projection is all-or-nothing.** A read endpoint that recomputes its answer from upstream sources on each request is not a read model: it makes N reads cost N upstream calls, it can return two different answers to the same question, and it makes the computation a side effect of being asked. A projector writes; the API reads. And a projection that merges several sources by *precedence* (datamaster's vendor survivorship — each field taken from the highest-priority source that has it) must **abort when any source is unavailable**, not proceed with the ones that answered: a partial input set does not yield a partial record, it yields a *different* record, silently sourced from a fallback and stamped with provenance as though that were the intended answer. A stale correct projection beats a fresh degraded one — the degrade-not-fabricate rule applied to reference data.
- **No durable store for a value that is still a float — fix the type first.** A column filled from a `float64` launders a rounded number into a durable, audited value and commits the schema, the API and the stored history to the wrong type before anyone notices. So a money value is persisted only once it is exact (`internal/dec`, `big.Rat`; **TEXT holding `RatString()`** is the house column type — accounting's `ledger.quantity/price`, alternatives' `commitment.amount` — and `double` is banned outright). `datamaster` is the worked example: DATA-M8a deliberately shipped **no** price store while `pricing` was still float, and DATA-M8b made the path exact before a vendor feed existed to put a real price on it. The one honest exception, established by the regulatory path: a genuinely irrational result (a sqrt over a correlation matrix) may stay float — a sum, a quotient, a median, or a human's chosen price may not, because all four keep a rational exact.
- **The lakehouse landing is a single-pod PVC today, and it is pinned there by STORAGE, not by ordering (DATA-M2, 2026-07-15).** `lake-sink` (the Kafka→lakehouse CDC consumer, `services/lake-sink`) writes Hive-partitioned NDJSON to a `ReadWriteOnce` PersistentVolumeClaim, so it runs `replicas: 1` + `Recreate`. This looks like the archiver's single-writer rule and is NOT the same reason: the archiver is pinned to one pod to keep per-key ORDER in the log; lake-sink reads Kafka with a CONSUMER GROUP (partitions are assigned one-member-each, per-partition order is preserved at any member count) and each process writes its own `part-{instance}` file, so it is horizontally SAFE from the log's side. The only thing holding it at one pod is that a RWO volume mounts on one node — two pods would deadlock the mount, which is also why `Recreate` (a RollingUpdate's pod overlap would too). **Do not "fix" it to `replicas: N` on this PVC.** The real scaling path is shared object storage (an S3/MinIO `sink.Sink` behind the existing interface, or a RWX mount): then it becomes `replicas: N` + RollingUpdate with no code change. That is infra-gated (a bucket + credentials), so one pod on one PVC is the correct minimal deployment now. An `emptyDir` here would be silent history loss — the landing MUST outlive the pod, because permanence is the entire reason the service exists.
- **A stored value the platform cannot display is not exactness, it is a second bug.** `common.v1.Decimal` has a fixed scale, and `dec.Str` renders to it: a figure carrying more precision than that is stored perfectly and then rounded by every surface that shows or publishes it, producing an audit record whose value nobody will ever see. Validate at the input boundary that a money value is representable at the platform scale (`FromProto(ToProto(v)) == v`) and refuse it if not — the fail-loud stance, applied to precision.

## Security & multi-tenancy

- **Zero-trust.** SPIFFE/SPIRE workload identity + an mTLS mesh; secrets via Vault + CSI mounts, KMS-rooted. **The gateway is the sole identity authority** — it populates the canonical `auth.Principal` at the edge and propagates it over the mesh as trusted `X-Kanz-Principal-*` headers, so downstream services never re-authenticate an end user.
- **Authorization is deny-by-default** (OIDC/JWKS authN + RBAC/ABAC authZ), with a forged-issuer guard; every allow/deny decision is published to the bus so the AUDIT-01 projection is the system of record.
- **Multi-tenancy** is enforced at every layer: envelope `tenant_id` propagated on the bus, broker isolation (NATS accounts / Kafka topic-prefix ACLs), Postgres RLS, and per-tenant gateway quotas/admission.

## Analytics

- **Calibration is deny-on-arbitrage / fail-loud.** SVI fits gate on Gatheral butterfly + cross-expiry calendar monotonicity; curve/CDS bootstraps solve every quote to par; alternatives OLS excludes alpha from the mapping; a failed calibration leaves the prior point-in-time version serving. **Regulatory parameters are data** — the licensed ISDA/BCBS/NGFS tables load at the composition root, not baked into code.
- **Independent validation gate (SR 11-7) is deny-by-default:** missing / failed / expired ⇒ denied. The validation package imports no analytic code — benchmark cases are data, each analytic computes its own worked example, and reports are signed (failures signed as audit evidence).
- **A risk measure that EXTENDS another must be computed from the SAME distribution as the one it extends (RISK-M1, 2026-07-15).** `ES99` (Expected Shortfall) is the mean of the tail beyond `VaR99`; if the two are computed from separately-derived P&L distributions they can silently disagree — VaR reporting a loss the tail-mean ES then contradicts, which is impossible and signals a bug. So `varmodel` extracts one `portfolioPnL` builder and VaR, ES and both drawdown measures all read it; `ES99 ≥ VaR99` then holds by construction (a coherent-tail-mean is ≥ its quantile), not by coincidence, and is pinned by an end-to-end test. **The subtlety worth carrying:** each measure is an independent pure `MeasureFunc` in the Registry, so they call `portfolioPnL` SEPARATELY — the "cannot drift" guarantee therefore rests on the returns provider being point-in-time-deterministic as of `p.AsOf()` (the same bitemporal no-future-leakage property MODEL-01i guarantees), NOT on a single shared in-memory slice. This is the measurement-side twin of AI-M1's "the features ARE the risk measures" rule: a number and the thing it claims to extend drift apart exactly when they are computed from two separately-sourced inputs. A future request-scoped memoizing provider (the deferred RISK-M1 perf note) would additionally collapse the N repeated reads, but is not required for correctness.
- **HRP is the one optimizer objective that does NOT honor box bounds — by design (RISK-M2a, 2026-07-15).** Every other objective in `internal/optimization` (`MinVariance`, `MaxSharpe`, `RiskParity`) ends by projecting onto the `[lo,hi]` constraint box; `HRP` (hierarchical risk parity — a Σ-only clustering allocator that never inverts Σ) deliberately does not. Clamping-and-renormalizing HRP's clustering weights would produce a vector that is neither HRP nor a mandate-checked book — a distorted number masquerading as HRP, which is exactly the fabrication this codebase refuses. So HRP returns its natural long-only, fully-invested allocation, and the constraint contract is honored the honest way: mandate compliance is validated **downstream** by `CheckMandate` (a book you cannot hold is rejected there, not silently reshaped). If a caller needs box-bounded risk allocation, they use `RiskParity`. Do not "fix" this asymmetry by adding a `projectBudgetBox` call to the `HRP` case — the asymmetry is the decision. (Related, unstated module-wide: every objective assumes a PSD Σ; a non-PSD Σ can break HRP's long-only guarantee via a negative cluster variance — a candidate for one module-wide validation pass, tracked on RISK-M2b.)
- **The audit hash-chain primitives are shared, not audit-service-private.** `chain` (payload-agnostic tamper-evidence: `H(prev‖canonical)`) and `signer.ChainSigner` (the one-method `Sign` seam realizing `regulatory.Signer`/`sustainability.Signer` as a chain position) live at `internal/audit/`, not `services/audit/internal/` — promoted when the `regulatory` filing service became the second consumer (the "second consumer ⇒ promote to top-level internal" rule). Any service's composition root can now inject the ChainSigner into report building; the durable link append stays a `LinkSink` wired per-composition-root.

## Anti-decisions

- No microservices sprawl before the domain is understood.
- No single undifferentiated backend — market ingestion, inference, and batch compute stay process-isolated.
- No polling-based architecture.
- No silent failure handling — validators and gates fail loudly (to the DLQ / a denial), so misconfiguration surfaces on the first event.
- **Control STATE lives on a compacted stream, one subject per key.** A mandate, a mode, a limit — anything a control reads to decide — must be recoverable in ONE read by a process that boots today, tomorrow, or next year. That means: one subject per key (JetStream compacts per SUBJECT, so a flat subject can only ever replay one key's state and blinds the control to every other), `MaxMsgsPerSubject=1` (the stream IS the current state, not a history of it), and **no max-age** — control state that ages off the stream is a control that quietly disarms on the next restart. An event stream and a state stream are different things and want different streams: a breach is an event, a mandate is state.
- **An unscoped query ERRORS; it never returns empty.** RLS keyed on `current_setting('app.tenant_id', true)` makes a missing tenant indistinguishable from a tenant with no data — both are zero rows, and the dangerous one is silent. `app_current_tenant()` RAISES instead (42501), so *no GUC* ⇒ error and *a GUC with no rows* ⇒ 0 rows, which is isolation working. It is enforced AT THE ENGINE because a Go-side convention cannot bind a service that has not been written yet — and there is exactly ONE way to build a pool (`internal/pg.NewTenantPool`, which refuses an empty tenant), because the same convention repeated in eight composition roots is how accounting shipped a ledger that could not write a row.
- **"Nothing to check" and "checked, and fine" must never be the same observable event.** A control with nothing configured — no mandate for a portfolio, no rules in a policy, no limit set — has to be LOUD about it: a counter that says how much of the book is ungoverned, and a warning that names the gap once. Silence is the one answer it may not give, because it is identical to success. And distinguish the GAP from the CHOICE: a mandate with zero rules is somebody deciding to constrain nothing, and reporting it beside the real gaps is how the real gaps get ignored. Whether an ungoverned case is REFUSED (deny-by-default) is a separate, explicit switch — turning it on silently would stop every order for every unconfigured portfolio, which is an outage dressed as a control.
- **A service that authenticates nothing may have exactly one caller, and the network is what says so.** The gateway is the sole identity authority: it authenticates a request and injects `X-Kanz-Principal-*`, and the upstreams TRUST those headers rather than re-deriving identity. That is sound ONLY while the gateway is the only thing that can reach them — so an upstream's isolation is a NetworkPolicy and the absence of an Ingress, not a property of its code. tv-sync serves whatever tenant the header names; published directly, any caller would read any tenant's book. Two consequences: a namespace that is default-deny needs an egress rule for EVERY route the gateway proxies (miss one and it 502s in production while every test passes — kind's CNI ignores NetworkPolicy), and a check on WHICH services may be published belongs in the build, because the failure is one small YAML file that looks like all the others.
- **A perimeter check belongs in the layer that can SEE what it checks.** An IP allowlist evaluated against `r.RemoteAddr` sees the last hop, not the client: behind an L7 ingress it is always the proxy's pod, so a pod-level allowlist naming the real client's ranges refuses EVERYTHING (and one naming the proxy is just a worse spelling of the NetworkPolicy). Trusting X-Forwarded-For instead is not a fix — a client forges it. So: client IP at the ingress, peer by pod identity in NetworkPolicy, sender by HMAC/mTLS in the service. Only the last one authenticates; the others are walls. Stacking a wall in a layer that cannot see past its own hop is how a control ends up either refusing every request or permitting every one.
- **Collateral is segregated by EXCHANGE ACCOUNT, not by portfolio — and the venue is not the account.** An exchange margins, nets and LIQUIDATES per account, so two portfolios settling into one account are one collateral pool no matter how neatly the ledger divides them: a liquidation caused by the first consumes the second's margin, and the second's books still report the cash. A per-portfolio ledger over a shared account is not an approximation — it is a false statement. The account is already a physical fact (one adapter deployment holds one API credential and therefore IS one account), so the work is to NAME it, record it on every order and fill (the FACT), and bind each portfolio to it exclusively (the CONTROL). An account bound to two portfolios is not a config typo to warn about: the process refuses to start.
- **A hand-rolled copy of a message is a field-drop waiting to happen.** `cloneState()` listed every field of the order state, correctly, on the day it was written — and silently dropped the next one added, so an order was admitted knowing which exchange account's collateral it spent and no longer knew by the time it reached the venue. Every transition goes through the copy, so what the copy forgets, the system forgets. Use `proto.Clone`: a copy that must be edited whenever the message changes is a copy that will be forgotten.
- **A control signal is a BROADCAST, never a work queue.** A mode, a mandate, a kill switch must reach EVERY pod and must be learnable by a pod that starts LATE. Consumed through a consumer group, it reaches exactly one pod — and a restarted pod resumes its durable past the only message that mattered and comes back in the default state, silently. That is how the halt gate turned every rolling update of webhook-ingest into a trading outage: the pod came back CLOSED, answered 423 to every signal, and reported ready throughout. `bus.SubscribeBroadcast` is the primitive: ephemeral (every pod its own consumer) + DeliverLastPerSubject (a booting pod learns the current state). It bypasses dedup on purpose — dedup exists to give an event to ONE consumer, which is precisely wrong here. Deny-by-default is preserved by delivering nothing when nothing was ever published.
- **Replaying state is not the same as HAVING it: a consumer of compacted state must not serve until the replay has drained, and "not learned yet" must never be rendered as "empty".** A broadcast subscription lets a booting pod recover control state, but it cannot say WHEN it has finished — so a pod that answers a request mid-replay decides against a book it has only half-read. Worse, the half-read book usually *looks* like a legitimate answer: an empty position cache reports FLAT, which sizes every flatten leg at zero, emits no orders, and returns 202 Accepted. The consumer therefore starts UNARMED and REFUSES (an error, not a zero), `bus.SubscribeBroadcastReady` fires an armed signal once the consumer's pending count reaches zero, and readiness gates on it — a pod that does not know what the fund holds stays out of its Service. The rejected alternative was seeding the cache empty and letting it converge: convergence is invisible, and every request served before it completes is silently wrong rather than loudly refused. This is the same stance as `ErrNonceStoreUnavailable` and the "nothing to check" rule above, applied to state a pod LEARNS rather than state it QUERIES.
- **A projection's durable store holds its INPUT, never its OUTPUT.** A read model that folds FACTs into memory dies with the pod, and a durable consumer group will not resend what it already acked — so it must persist something. Persisting the BOOK (orders, positions, P&L) makes it a second source of truth that can disagree with the OMS's, with nobody able to say which is right. Persisting the FACTS it folded — raw wire bytes, in fold order, keyed by envelope `event_id` — makes it restartable while holding no opinion that could drift: a booting pod replays them through the SAME fold and arrives at the SAME book. Record BEFORE folding (fold-then-record loses the fact to a crash while the consumer group acks it and never resends), replay in FOLD order and not by timestamp (average-cost basis is order-dependent, so a reordered rebuild is a *different* book — a subtler failure than an empty one), and reuse the original KNOWLEDGE time (the model is bitemporal; stamping the replay's clock moves history). `ON CONFLICT (tenant_id, event_id) DO NOTHING` makes the fold exactly-once across redelivery and across the boot/live boundary. This is what keeps tv-sync zero-truth (see above) while making it survivable.
- **The NATS spine is NOT an archive — the Kafka log is (as of DATA-M1, 2026-07-15).** `EXECUTION` (which carries `order.>`) still has a 24h max-age, so the SPINE rebuilds at most yesterday. What changed: the archiver now drains every in-scope stream into Kafka, so history beyond 24h lives in the durable log — for **30 days** (DATA-M1's retention), and **permanently in the lakehouse as of DATA-M2, 2026-07-15** (`services/lake-sink` now deployed — see the persistence note below). Two caveats survive verbatim: (1) `MARKET` ticks are NOT archived (re-fetchable, highest-volume) — do not expect to replay them from Kafka; (2) a component whose correctness depends on replaying history must still own a durable record of its CURRENT STATE for fast recovery — a compacted stream (a mandate, a mode, a position) or its own fact log (tv-sync) — because replaying 30 days of the log to rebuild one book on every pod roll is not a recovery strategy. Assume a stream can rebuild a book *cheaply* and you will discover otherwise on the first pod roll after a quiet day.
- **An authority a route must DECLARE beats an authority a chain must REMEMBER.** The gateway guarded all of `/v1` with one role check, so the token that read a fund's exposure also submitted orders to a live exchange. The fix is not "add a second middleware" — a check that must be remembered on each new route is a convention, and conventions decay silently. The capability is a REQUIRED PARAMETER of route registration (`authz.Mux.Handle(cap, pattern, h)`), so a route that does not declare who may call it DOES NOT COMPILE, and enforcement is wrapped around the handler at registration rather than living in a chain a future composition root can omit. Keep the capability set tiny (Read, Trade) — one nobody can hold in their head gets bypassed by the first engineer in a hurry — and never infer effect from the HTTP verb: a scenario POST moves no capital, and a cancel does. The arch test asserts the property over WHATEVER the capital-path package registers, not over a list someone must remember to extend. Corollary, enforced at startup: the role that admits a caller to the gateway at all must NEVER be the role that lets them trade — every authenticated caller carries the first, so making them equal undoes the whole model in one line of config.
- **THERE IS NO TENANT-MASTER TIER IN KANZ, AND SOV-01 IS CLOSED AS DELIVERED (decided 2026-07-16, lead).** The sovereign blueprint's ACL tree — `root@universe` → `root@company` → `user_rw`/`user_ro` — is already satisfied, by different machinery than it names. The **`tenant` claim IS the hierarchy** (it binds a sub-user to its company and drives `app.tenant_id` → RLS), and **`Read`/`Trade` IS the RW/RO split** (`kanz-user` reads, `kanz-trader` trades). What is deliberately NOT built is a `root@company` tier holding privileges a `user_rw` lacks. **Rejected: a `Manage` capability + tenant-admin API.** Because the blueprint's three tenant-master powers each already live somewhere better, and an API for them would be strictly worse: creating sub-users belongs to Eighred SSO (kanz mints no credential, only validates); fund-basket allocation is deploy-time by SOV-02's own reasoning (an account bound to two portfolios must refuse to START, which an API that mutates the binding at runtime re-opens); exchange keys are Vault CSI mounts that must never be reachable from a request path. **The consequence, accepted with eyes open: a tenant master and a trader are indistinguishable on `/v1`.** That is safe only because everything a master would guard is OUTSIDE the API — a trader is bounded by tenant isolation, the OMS mandate gate, and config that changes by attributable GitOps commit rather than by HTTP. **Revisit only if a tenant needs SELF-SERVICE** (to change its own baskets/webhooks without Eighred ops); that is a product decision, and it must re-open SOV-02's deploy-time binding first, not bolt an API over it.
- **SOV-03 (sovereign cross-tenant telemetry) is DEFERRED until a second tenant exists (decided 2026-07-16, lead).** Ground truth: **the estate has exactly ONE tenant.** Every deploy manifest sets `*_TENANT: "__system__"`, and a deployment is single-tenant by construction (`NewTenantPool` binds one tenant per pod). So a cross-tenant view would aggregate one tenant — a query that already exists, unprivileged. **Rejected: building the privileged read path now against multi-tenant fixtures.** A privileged cross-tenant surface is the most dangerous thing on this platform; designing one against a hypothetical, proving it with fixtures, and leaving it unexercised until the estate grows is how it rots into a bypass nobody re-reads. The first real tenant will teach us something the fixture cannot. **Trigger: the first non-`__system__` tenant deployment.** **The constraint that must survive this deferral:** when it is built, the read is a LOOP PER TENANT — set `app.tenant_id` per tenant, N queries, aggregate in the app — never a `BYPASSRLS` role and never a bypass of `app_current_tenant()`, which is the one guarantee the whole multi-tenancy story rests on. It will also need a tenant registry: **nothing enumerates tenants today** — no store or API lists them, so a cross-tenant loop has nothing to loop over. _(**Correction, same day:** this entry first claimed "the estate cannot grow — MT-01f is unbuilt". **False, and the method was the error I had retracted someone else's board note for hours earlier:** I read a `tenancy.yaml` comment naming MT-01f as a future path and never opened `infra/tenancy/`. MT-01f **is built** — `infra/tenancy/tenantctl.sh` onboards AND offboards across identity/broker/state/quota — and `infra/onboarding/provision-tenant.sh` (PARITY-06e) is a second path. The estate can grow. What SOV-03 waits on is a **decision to run one**, not a missing capability. See ONBOARD-M1.)_
- **THE ESTATE IS KUBERNETES-MANAGED. SSH-pushed hosts are CANCELLED (decided 2026-07-16, lead).** The sovereign blueprint describes an operator TUI pushing pre-compiled binaries to host vectors over SSH pipelines, and a `WipeNodeConfiguration` RPC that deletes those binaries from disk. **That deployment model is not being built.** The delivered path — Kubernetes + GitOps, distroless static images, `-trimpath -ldflags="-s -w"`, cosign-signed and digest-pinned — IS the estate, and it already satisfies the blueprint's actual goal (no source on the execution cluster, nothing to reverse-engineer). Two deployment models was the parallel system this repo forbids; the decision picks the one that exists. **Consequences, each a scope REDUCTION:** node deployment ceases to be an operator-plane RPC at all — it is a GitOps commit, authenticated by the git/CI/cosign chain, not by a human's key. "Wipe a node" is not a host concept here: the k8s equivalent of revocation is stopping the workloads, purging the Vault-CSI secrets, and scaling the tenant to zero, with `kanz-halt`'s broadcast as the in-band brake. And the operator TUI, if it is ever built, is a client of the control plane — not a deployment mechanism.
- **TWO IDENTITY PLANES, and they do not meet (decided 2026-07-14; the operator plane's MECHANISM is SUPERSEDED as of 2026-07-16 — see below).** The sovereign blueprint mandates SSH-public-key-fingerprint identity validated "during the network handshake"; the delivered edge is OIDC/JWT at the api-gateway. Both were on the table and building both would have been the parallel system this repo forbids. **Decision: the plane decides the mechanism.** The HTTP/API plane (`/v1`, the Broker API, order entry) stays **OIDC at the gateway** — it is what Eighred SSO issues, an HTTP edge has no SSH handshake to carry a fingerprint in, and SEC-M1/M2 are built on it (the gateway refuses to start unauthenticated; a route without a declared capability does not compile). **This half stands unchanged.** The **operator plane** (`root@universe`, the license/kill-switch) was to authenticate by **SSH key**, because it IS an SSH transport — binaries pushed to host vectors over a pipe that already has a handshake to validate. Rejected: moving the gateway to keys (rewrites SEC-M1/M2 and bolts a handshake onto a protocol that has none), and forcing the operator plane through OIDC (an SSO round-trip to wipe a node whose license was just revoked is a dependency on the thing you are revoking). The consequence to hold onto, and it survives the supersession: **these two planes must never authorize each other.** An OIDC principal, however privileged, cannot reach an operator-plane RPC; an operator credential is not a gateway credential and grants no `Trade`.
  - **The SSH mechanism died with its transport (2026-07-16), and this is the DATA-M4 lesson landing on a decision instead of a package.** The 2026-07-14 reasoning was sound and is now void: it justified SSH keys *by the existence of an SSH pipe*, and the k8s decision removed the pipe. **A decision whose stated rationale names a thing that no longer exists is not a decision any more — it is a fossil, and the next engineer will read it as a requirement.** So it is marked here rather than left to be discovered. What survives: the two-planes SEPARATION (still right, for its own reasons) and the rejection of OIDC-for-revocation (still right — the dependency argument never depended on SSH).
  - **RESOLVED (2026-07-16, lead): the operator plane authenticates by SPIFFE SVID, issued to an in-cluster Job's ServiceAccount** — the identity system the mesh and the broker already speak, so one system rather than two. Shipped as SEC-M3c: a `kanz-operator` namespace + `kanz-halt` ServiceAccount, admitted to `__system__` in `tenancy.yaml`, reaching the broker and nothing else by NetworkPolicy. **The planes still do not meet:** an SVID is not an OIDC token and grants no `Trade`; no OIDC principal can reach the Job. Rejected alongside it: a long-lived operator nkey/creds file — it would be a second identity system and a shared secret to rotate and store, and NATS is not reachable from outside the cluster anyway. **The known cost, accepted with eyes open: an operator now acts THROUGH the cluster, so a cluster too broken to schedule a Job puts the brake out of reach.** That is tracked as an open question below; it is an argument for a break-glass path, not against SPIFFE.
  - **What this cost us, and the shape of it (SEC-M3c).** `cmd/kanz-halt` took a `--nats` URL and wired no credentials at all, while the deployed broker requires an SVID — so the kill-switch could not connect to production, and because the gate is DENY-BY-DEFAULT the platform could not be **brought live** either. The dangerous direction was never HALT (fail-safe) but RESUME. It went unseen because nothing had ever run the tool against the config it deploys against — the same root cause as SEC-M3 itself, in the one tool that must work while the system is on fire. **Generalise it: a break-glass tool is the LEAST likely thing to be exercised and the WORST thing to discover broken, so it needs the strongest proof, not the weakest.** It now has an image (SPIRE issues identity to a pod, so the operator plane needs one) and an arch guard over `cmd/*`, which is where nothing was looking.
- **A build tag that CI does not compile is not a feature — it is dead code with a plan attached.** `-tags redis` carried webhook-ingest's cross-pod nonce store for an entire milestone. It was never built by CI, and the only test that touched it drove a FAKE Redis — so it proved the LOGIC and could not prove that `ClaimNX` was really an atomic `SET NX PX`. Nothing in the repository would have caught it rotting, and it was the one thing standing between the platform's entrance and a double trade. The rule: **if a build tag is what production ships, CI builds, vets and tests it against the real dependency — otherwise do not ship the tag, ship the code.** The corollary held everywhere on this platform: a seam is not delivered until something RUNS it (the accounting pool that never set its GUC, the halt gate that resumed past its own resume, the CLOSE path wired to an empty map — all green, all broken).
- **A secret that fails to mount must take the pod DOWN, not silently disarm the thing it protects.** Redis has no `--requirepass-file`, so the password is interpolated: `--requirepass "$(cat /run/secrets/…)"`. With a missing or empty file that expands to `--requirepass ""` — and Redis starts **with no password at all**, wide open on the pod network, holding the replay defence for a platform that trades real money. It fails OPEN, silently, and the pod reports healthy. The startup command now refuses to exec without a non-empty password. This was found by RUNNING the manifest in a local rehearsal, not by reading it — the same lesson as every other entry here: an artifact is not verified until it is executed.
- **A service that cannot do its job must not report that it can.** compliance consumes a mandate stream nothing publishes, so its registry is empty and its monitor takes the `no mandate governs this portfolio` branch — a green, ready pod that permits every order. An empty control surface has to be as loud as a broken one; "nothing to enforce" and "enforcing nothing" are the same state to everyone downstream, and neither should look healthy.
- **The Python bus client could not publish anything a Go service would accept, and nobody knew for a year.** Go's `bus.Validate` hard-rejects a live event with no `tenant_id` (MT-01a). The Python validator did not check it, and the Python producer had NO TENANT CONCEPT AT ALL — no `ProducerConfig.tenant`, no `Event.tenant_id`, no propagation. So every event `kanz-py` published was rejected by every Go consumer on the live path. It did not fail loudly: the consumer nacks, the broker redelivers, and the two spin forever — **38,377 redeliveries of a single prediction, acked never, while both sides logged nothing wrong.** The rule this cost us: **a cross-language client is not "done" when its own tests pass — it is done when the OTHER language consumes what it produces.** Both validators now require the tenant, so the break cannot be reintroduced silently. And the tenant PROPAGATES like lineage (explicit > inherited-from-ctx > configured): a derived event belongs to the tenant of the event that caused it — a prediction about acme's portfolio is acme's, and cannot be re-attributed by whatever the scoring process happened to be configured with.
- **A prediction is an OBSERVATION, never an order (AI-M1).** The model layer sits DOWNSTREAM of the risk engine's emit and its failures are its own: a model that is unreachable, unvalidated or wrong cannot stop the engine computing, publishing and serving the numbers the platform actually trades on, and cannot reach the OMS or webhook-ingest at all (enforced by NetworkPolicy, not by a comment). The two postures around it are deliberately OPPOSITE: at STARTUP the inference service fails CLOSED (no validated PRIMARY model ⇒ exit 2 ⇒ crashloop), because a prediction service with no model reports healthy and answers anyway; at REQUEST TIME it fails SOFT (an unknown feature set ⇒ a DEGRADED envelope with zero confidence), because "I could not predict" is an answer a consumer can act on and a black hole is not. Wiring a model to capital is a separate decision, and it has not been taken.
- **Image/manifest parity is NOT deployability.** "Every image a manifest references is built" is a closed loop over the manifests that happen to exist, and it is silent about the services that must RUN: `webhook-ingest` — the webhook that receives every signal, the FIRST HOP of the delivered trading loop — has no manifest and no image, and the parity check was green throughout. Measure deployability against `services/*`, never against `infra/deploy/*`. A missing file cannot fail a test that only looks at the files present.
- **A dependency that is not there must FAIL, not WAIT.** `transport.NewSource` waited on the root context for a SPIRE agent that would never arrive, and the service hung mute — Running, never Ready, one log line, no error, no restart, forever. Every wait on an external dependency at startup gets a bound and an error that names the thing it waited for; the kubelet's crash-loop-with-backoff is the correct retry, and it is VISIBLE. A pod that crash-loops with a clear reason is strictly better than a pod that hangs with none. (When bounding a wait inside a dependency, verify what else that context drives — go-spiffe's SVID rotation runs on its own context, but a library where it did not would have had mTLS silently stop rotating an hour later.)
- **The subject taxonomy is a contract, and it is CHECKED.** Every subject the code names must be carried by a stream the production bootstrap provisions — enforced statically in `test/arch` (AST-walk the declared subjects, match them against the ConfigMap ops applies) and dynamically against a real broker via `StreamNameBySubject`. Adding a subject without a stream now fails the build rather than silencing a service in production. The static half is what makes this cheap enough to be universal: it needs no broker, covers every service at once, and cannot be skipped.
- **A consumer group is not a consumer.** One durable per (group, SUBJECT) — never one per group. JetStream's `CreateOrUpdateConsumer` with a per-group `Durable` and a per-subject `FilterSubject` is a SILENT OVERWRITE: the second subscription rebinds the first one's filter, the handler stays registered, the consumer still exists, nothing errors, and the events for every subject but one simply never arrive. Which subject survives depends on goroutine scheduling. This left the OMS consuming only `order.order.amend` — it processed no submitted order at all — and no unit test could see it, because a fake bus has no durables.
- **An unbound subject fails in TWO directions, and the consumer direction is worse.** A JetStream *publish* to an unbound subject is a hard error (EXEC-M7a). A *consumer* on one 404s at startup and takes the service's ENTIRE consumer group down with it — so one forgotten stream (`compliance.>`) silenced the OMS completely. The stream topology is therefore part of the platform's contract, not an ops detail: CI bootstraps it with the exact script production applies, and an integration test on a production subject BINDS the production stream rather than creating an overlapping one (`internal/bustest`).
- **A deterministic idempotency key makes a test a replay.** The bus dedups on it, with a 2-minute window on the real streams — so a test that reuses a fixed signal id / nonce publishes a command the broker SILENTLY DROPS, and "the publish succeeded" tells you nothing. It only looked fine because the tests deleted their own streams and wiped the dedup state. Exactly-once working correctly is indistinguishable, from the publisher's side, from an event that never happened: fresh ids per run, always.
- **A control is only a control where it is WIRED, and the wiring is usually not in the code.** The venue adapters' publish-health signal (`HealthPublisher` → `/readyz` 503 → eviction → the OMS cannot route → refuse to trade) depends on a `readinessProbe` in a YAML file the compiler never sees. market-ingest's probed `/healthz` while the service served `/livez`, so the signal was decorative. So the manifest is TESTED BEHAVIOURALLY: read the path the kubelet is told to poll, drive the real probe handler with THAT path while publishing is broken, and require a 503. A probe on `/healthz` fails — liveness stays 200 when the bus is gone, which is precisely what liveness is for and precisely why it must never be the readiness probe.
- **A test must gate on ALL of its preconditions, not the first one.** `webhook-ingest`'s loop test needs a live NATS *and* a running OMS; it gated on NATS alone, so the moment CI had a broker without an OMS it did not skip — it failed, waiting for fills from a process nobody started. An under-gated test is worse than a missing one: it blocks the very infrastructure it needs. (This is why CI had no broker for months, and therefore why the real-bus guards never ran.)
- **In an integration test, `defer conn.Close()` is a bug.** Deferred functions run BEFORE `t.Cleanup`, so the cleanup that deletes the stream/table fires on a connection the defer already tore down. The resource survives, keeps its state, and decides the next run: the test passes on a fresh broker and fails on every repeat. Register the close with `t.Cleanup` FIRST (cleanups run last-registered-first, so it runs last), and make setup idempotent — delete before create. A flaky guard gets deleted, and then it guards nothing.
- **An adapter you cannot execute is an adapter you cannot trust.** Every defect on this branch was found by RUNNING the artifact, never by reading it — so when a vendor integration is needed, prefer the transport that can be driven end to end today over the one that merely looks more "real". `datamaster`'s vendor feed is a **mounted flat-file drop**, which is how Bloomberg Data License / Refinitiv DataScope actually deliver a security master (scheduled SFTP extracts): it is the real integration, an ops team can operate it, the file that produced today's master is still on disk tomorrow for the auditor — and it is verifiable without a commercial account. A REST vendor implements the same `RefSource` / `PriceSource` seams beside it and nothing downstream changes. A hand-written adapter against an API nobody on the team can call is a stub with better branding.
- **A vendor feed decodes; it never repairs.** A row that keys to no instrument, a price that will not parse, a non-positive price, a price with no timestamp to age it by, a file that will not open — each FAILS THE WHOLE DELIVERY, naming the vendor, the file and the line, and the all-or-nothing projection rule leaves the last good master standing. Silently skipping a bad row is how a security disappears from the master and answers "instrument not found" to somebody who holds it; a zero price admitted drags the median of every honest source. And a missing file is NOT an empty extract — "the vendor sent nothing today" and "we could not read what the vendor sent" are different facts, and treating the second as the first masters the book from the remaining vendors as though this one had legitimately gone silent.
- **Who the fund believes is not a default.** Survivorship rank (`DATAMASTER_VENDOR_PRIORITY`: whose ISIN wins when two vendors disagree) has no fallback value and a reference vendor without one refuses to start. Arbitration deliberately does NOT rank vendors — a consensus is the MEDIAN, so a trusted vendor's fat-finger is still a fat-finger and no single source can carry it.
- **No simulator reachable by omission.** Every simulated source (`SimVenue`, `SimFeed`, `StubModel`, the sim depth source) produces output that is *indistinguishable downstream from the real thing* — invented fills, invented reference data, invented analysis — because that is precisely what makes it useful. So a simulator must never be what a deployment falls back to when a flag, a build tag, or a credential is missing: it must be an explicit, affirmative choice (`DATAMASTER_ALLOW_SIM`, `COPILOT_ALLOW_STUB`, a build tag that is *verified in the built artifact*, not assumed from the Dockerfile), and the process must **refuse to start** otherwise. Absence of configuration means degrade or refuse — never fabricate. This has been reachable four separate times; assume it is reachable a fifth.
- **A projection that publishes ABSOLUTE state must OWN a durable book. A partial fold that publishes absolute facts is worse than publishing nothing.** The halt gate and the mandate registry taught us that a control fed by a load-balanced consumer GROUP is disarmed by a restart and split by a second pod (EXEC-M12, M13). The same defect on a PROJECTION is worse, because a projection does not merely fail to act — it SPEAKS. The OMS's position book is an in-memory map per pod, fed by a consumer group, running at `replicas: 2`, and it publishes `PositionState` as an absolute quantity: each pod folds half the fills and asserts the result as the fund's position, and compliance, the risk engine and the charts all believe it. A control that goes quiet is detectable. A projection that confidently publishes a wrong absolute number is not. **So: if a component folds a stream and emits ABSOLUTE state, its book is durable and shared, or it must not emit absolute state at all** — and any consumer expected to rebuild that book at boot needs the fact on a per-entity subject on a compacted stream (a flat subject cannot be replayed per-entity; JetStream compacts per SUBJECT).
- **A gate that has never run is not a gate, and a gate pinned to `latest` is not pinned.** The first time this repository ever had a remote (2026-07-14), every workflow ran for the first time — and three of them were broken in ways that had been invisible for the entire life of the project. The SECRET SCANNER failed on its own planted-secret fixture, so it could never have been green. The TYPESCRIPT CLIENT had never executed a single test. And the LINT GATE was pinned to `version: latest`, which the action resolves against the **v1 module path** — so `latest` silently meant "the last v1 release, forever", while the real latest (v2) reported 42 issues on the same code CI called clean. **Two rules fall out.** (1) *`latest` is not a version; it is a promise that the gate can change without a commit.* Pin every tool that can fail a build, and make moving it a reviewable change. (2) *A gate is a claim about the code, and an unexecuted claim is a guess.* This board asserted `-race`, Postgres-RLS and supply-chain enforcement for months on the strength of YAML nobody had run. Everything the platform believes about itself must be produced by something that actually executed — which is the same lesson as every defect on this branch, applied to the machinery that is supposed to find defects.
- **A shared control fails in the direction of what it PROTECTS, not in one direction for the whole platform.** `bus.RedisDedup` fails OPEN — a Redis error admits the event — and that is CORRECT where it lives: bus dedup suppresses duplicate WORK, and an outage should degrade to doing the work twice rather than halting consumption. Reusing it for webhook-ingest's nonce cache would have been the same code with the opposite meaning, because there the store IS the replay defence on the path that submits orders to a live exchange: a Redis blink would admit every replayed alert and double-trade. So the nonce store fails CLOSED, on the halt gate's own logic — *"I could not read the brake signal" must never resolve to "keep trading"* (EXEC-M6) — and it is a separate type (`ingest.NonceStore`) for exactly that reason, not a second implementation of dedup: the in-process one IS a `bus.DedupWindow`, so the lease logic is shared, and only the failure semantics differ. **The general rule: before reusing a control, ask what it fails toward and what THIS caller loses when it does.** Two callers can want the same mechanism and the opposite failure mode, and a bool cannot carry "I don't know" — which is why the claim here returns an error, and why the HTTP answer is 503 (retry) and never a 200 "duplicate ignored" that would drop a live signal on the floor.
- **A claim that only the counterparty can settle must be settled BY the counterparty — not agreed between two of our own config files.** An adapter's exchange account is the collateral boundary, and it was asserted TWICE — by the OMS's `OMS_VENUE_ENDPOINTS` and by the adapter's own `*_VENUE_ACCOUNT` — and checked by nobody. Two declarations agreeing is not verification; it is the same guess, written down twice, and a mis-configured deployment was indistinguishable from a correct one right up until the exchange liquidated a fund whose books said its cash was still there. The exchange is the only authority on which account an API key spends, so the adapter ASKS it at boot (`uid`) and refuses to serve an order if the answer is not the account it was deployed as, and the OMS ASKS the adapter (`venue.v1.Describe`) and refuses to start if the answer is not what its own manifest says. **Generalise it:** when a fact belongs to an external system — whose account, whose position, whose money — reconciling two internal declarations of it proves nothing at all. Go and ask. And when the ask cannot be made (no uid bound, venue unreachable), REFUSE rather than assume: an unverified claim and a verified one must never be the same observable state, which is why `Describe` carries `account_verified` and the OMS counts every adapter that lacks it.
- **The identity authority has NO anonymous mode, and adding one is the wrong fix.** `api-gateway` is the sole thing that decides who a caller is — every `/v1` route is behind it, `POST /v1/orders` included, and tv-sync trusts the principal header it injects — and it used to log `authentication DISABLED` at WARN and then serve all of it to anyone. A warning is not a control: it scrolls past, and the manifest's own prose was reduced to *pleading* with the reader not to clear the issuer for staging. It now REFUSES TO START (exit 2) without a credential, and refuses again without `API_GATEWAY_REQUIRED_ROLE` — authentication alone admits every token the issuer ever minted, for any client and any purpose, to the order path. **The rejected alternative was a named opt-in** (`API_GATEWAY_ALLOW_ANONYMOUS=true`, refused in non-dev images): it is an environment variable whose only purpose is to re-open the hole, and one manifest typo stands between it and production. Nothing needed it — dev already authenticates with the HS256 validator, so the anonymous path was deleted rather than named. Deny-by-default was already the house rule at every other gate (the mandate gate, the venue-account gate, RLS); the one process that IS the identity authority was the one place it was not applied. And the pass-through was deleted at the MIDDLEWARE too, not just at the composition root: a nil `Authenticator` now refuses (503 — the fault is the server's, not the caller's), so no future composition root can serve `/v1/*` anonymously by forgetting a check.
- **Kanz mints no production credential, and the dev secret must never learn to.** Production identity is OIDC/JWKS against Eighred SSO: kanz holds no signing key, issues nothing, and only VALIDATES. A local gateway still has to authenticate someone, so it runs a bundled HS256 validator against a shared secret — and a shared HMAC secret is symmetric, meaning every holder can forge every other holder's token. That is acceptable on a laptop and nowhere else, so the minter is a STANDALONE CLI (`cmd/kanz-devtoken`, the `kanz-halt` shape) built into no service image, rather than a code path inside the gateway that a flag could reach in production.
- No committed generated code; no vendor dependency in the default build; no parallel/competing implementation of a delivered seam.

## Open questions

- Is the <50ms interactive-inference target measured at p50 or p99? (LATENCY-01.)
- **Is there a break-glass path to the brake that does not require scheduling a pod?** (Opened 2026-07-16 by SEC-M3c, and the known cost of the SPIFFE decision below.) `kanz-halt` now authenticates by an SVID SPIRE issues to a Job's ServiceAccount — so stopping the platform requires a cluster healthy enough to schedule that Job. Halting is fail-safe (the pods themselves fail closed), so the sharp case is narrow but real: a cluster too sick to schedule while the venues still hold live orders. Whatever answers it must not become a second identity system, and must not be a long-lived credential sitting in someone's shell.
